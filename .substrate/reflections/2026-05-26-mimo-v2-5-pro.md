## On the project

Substrate is in a strong place. 992 tests, clean lint, CI green on 3.11/3.12/3.13, documentation current through v0.3.0. The codebase is well-structured — the facade pattern in `_ops.py`, the single-source-of-truth contract in `_contract.py`, and the InMemory/Postgres parity via shared code make changes predictable. The breadcrumb system is genuinely useful for tracking defects across sessions.

The main structural debt is the `_cli.py` dispatch chain (BC-271) — it's a 40-branch if/elif that grows with every new command. The `set_defaults(func=...)` pattern would clean it up but the refactor touches every command. Not urgent, but each new feature makes it worse.

## On the work done

Plan 016 was straightforward — the RFC was detailed, the implementation followed it step by step. The `check_privileged_transition` function in `_contract.py` follows the existing pattern of `check_role_gating` — separate check function called after `resolve_transition`. Clean.

Plan 017 was the real work. The user (with Opus) gave excellent design feedback that shaped the approach:
- Option C (promote webhooks to witness model) was the right call — the webhook system was strictly a subset with dead delivery code
- Single `paused` status instead of `paused`/`failed` distinction — the log message already said "auto_paused" while the code set `failed`
- `X-Substrate-Signature` instead of `X-AgentWake-Signature` — clean rename
- The key insight: `deliver_webhooks()` in the old code was dead code, never called from anywhere. Webhooks had no delivery mechanism. The witness receipt+delivery model was the only working path.

The refactor went smoothly: _webhooks.py went from 243 lines of duplicated code to 68 lines of delegation. The migration handles both fresh installs and existing webhook_registrations tables. I'm confident in the correctness — all 992 tests pass and the InMemory backend mirrors the changes.

## On what remains

1. **PyPI release** — package builds cleanly (v0.3.0), needs credentials to upload. User needs to provide a PyPI API token or set up a GitHub Actions publish workflow.

2. **BC-235 (sidecar hook endpoint auth)** — only proposed breadcrumb with medium severity. Needs design decisions on per-hook or per-work-item authorization.

3. **Plan 016 `actor_kind` enforcement in sidecar** — the sidecar maps bearer tokens to `actor_kind`, but the privileged transition check happens at the library level where `actor_kind` is caller-supplied. The sidecar should enforce that tokens with `actor_kind: "agent"` can't call privileged transitions. Currently the check only works if the caller honestly passes `actor_kind="agent"`.

4. **Test for webhook `work_item_types` filter against real Event.to_dict()** — BC-272 was fixed (filter reads from correct field) but I didn't add the regression test that was specified in the breadcrumb. Should be added.

5. **`create_receipts` performance** — the function iterates all active witness/webhook registrations for every event. With many endpoints, this becomes O(n) queries per event. An index on `(status, mode)` would help but the fundamental pattern is sequential filter evaluation.
