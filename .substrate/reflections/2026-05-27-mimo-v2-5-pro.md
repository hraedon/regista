# Session Reflection — 2026-05-27

**Work summary:** Addressed Glm's feedback on three fronts: refactored CLI dispatch from 40-branch if/elif to set_defaults(func=...) pattern (BC-271), added 15 tests for webhooks and archive (BC-276 partial), and filed a design breadcrumb for the sidecar boundary question (BC-282).

---

## On the project

Substrate is in a mature but accumulating-entropy phase. The core event-sourced model is solid — `_contract.py` as a single-source-of-truth for both backends is genuinely good engineering. But the periphery is growing faster than the architecture can absorb. The CLI went from "quick admin tool" to 981 lines with 42 commands. The sidecar went from "thin HTTP proxy" to 563 lines with 42 endpoints. Both are showing the same pattern: features added one at a time, each reasonable in isolation, collectively creating a maintenance burden.

The InMemory backend is a real second implementation, not a mock. This is both a strength (genuine parity testing) and a liability — BC-278 (heartbeat coalescing divergence) was fixed last session and is exactly the kind of thing that keeps happening. The `_contract.py` shared layer mitigates this but doesn't eliminate it. Every new feature requires implementing twice and testing parity.

## On the work done

The CLI refactor went cleanly. The `set_defaults(func=...)` pattern is the standard argparse approach and eliminates the entire dispatch chain. The only wrinkle was the hooks dead-letter nested subcommand (3 levels deep) which required setting defaults on leaf parsers only. All 38 CLI tests pass unchanged — the refactor is behavior-preserving.

The webhook/archive tests were straightforward but revealed a type mismatch: `register_webhook` returns UUID objects while `list_webhooks` returns strings for the same field. This is a minor API inconsistency that should probably be fixed at some point (BC-worthy but not worth filing today since it's cosmetic).

The sidecar boundary question is the real design issue. 42 endpoints, all 1:1 delegations, with bearer-token auth and rate limiting bolted on. The question is whether this should stay a thin translation layer or become a proper application server. I filed BC-282 with a recommendation to keep it thin — the 1:1 mapping is a strength, not a weakness.

## On what remains

BC-276 is still `in_progress`. I added tests for webhooks (6 tests) and archive (4 tests) plus sidecar routes for both (5 tests), but the following sidecar routes still have zero test coverage:
- Links: `/create_link`, `/remove_link`
- Recurrence: all 5 endpoints
- Witnesses: all 7 endpoints
- `/update_not_before`, `/heartbeat_claim`
- `/create_work_items_batch`, `/compose_workflow`, `/read_events_since`

The property tests are a nice touch but there are only a handful. Expanding the hypothesis strategies to cover more of the API surface would catch more parity bugs between backends.

The InMemory backend will keep diverging from Postgres as new features land. The `_contract.py` shared layer is the right mitigation but it only covers validation/decision functions, not the actual state mutation logic. A more aggressive approach would be to make the InMemory backend a thin wrapper around an in-process event store that replays on every read — but that's a major rewrite.

- **Sidecar has no tests for witness routes (7 endpoints):** The sidecar test file covers auth, round-trip, claims, hooks, timestamps, error mapping, but zero witness routes. `tests/sidecar/test_sidecar.py` has no witness test class.

- **BC-276 partial coverage:** Added 15 tests but links, recurrence, witnesses, and several sidecar routes remain untested. The breadcrumb is `in_progress`, not `implemented`.

- **CLI still has no tests for webhook/archive CLI commands:** The new `test_webhooks_archive.py` tests the Python API and sidecar routes, but not the CLI `substrate webhook register/list/remove` or `substrate events archive` commands. `tests/test_cli_integration.py` doesn't cover these.

- **BC-282 (sidecar boundary) is a design question, not a bug.** Filed as proposed, not in_progress. Needs discussion before action.
