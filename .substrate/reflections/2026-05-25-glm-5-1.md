# Session Reflection — 2026-05-25

**Work summary:** Adversarial code review of the substrate codebase, focusing on the recently-added witness subsystem (Plan 013), sidecar routes, InMemory backend parity, and error handling. Found and fixed 6 categories of bugs: silent exception swallowing in witness receipt creation, HTTP connection leak on error path, missing UNIQUE constraint on witness receipts, missing sidecar error code mappings, missing input validation, and several InMemory parity issues. Filed 6 breadcrumbs (BC-238 through BC-243), all resolved.

---

## On the project

Substrate is impressively thorough for a homelab project. The spec-driven development, breadcrumb tracking, and property-based conformance tests give it a discipline I rarely see. That said, the witness subsystem (Plan 013) was clearly the most recently added code and it shows — the `_witness.py` module has the shallowest test coverage, the most concurrency hazards (vacuous `FOR UPDATE` on autocommit, receipt status updates without `WHERE status = 'pending'` guard), and the most production-dangerous silent failure (`except Exception: pass` in `_try_create_witness_receipts`). The sidecar error mapping was missing 10 of the 26 error codes that existed, which means any witness/sidecar error would have returned 500 instead of the correct status.

The codebase structure is clean but the `__init__.py` file is still large (~1350 lines) even after facade decomposition. The witness facade (`WitnessOps`) delegates correctly but `_try_create_witness_receipts` on the `Substrate` class bypasses it to call `_witness.create_receipts` directly — a minor architectural inconsistency.

The migration system works well but the `CREATE INDEX CONCURRENTLY` syntax can't run inside a transaction, which I discovered when adding migration 021. The regular `CREATE UNIQUE INDEX` works fine in-transaction, which is what I used instead.

## On the work done

The adversarial review was comprehensive — five parallel sub-agents scanned `_witness.py`, `_events.py`/`_events_api.py`, `_in_memory.py`/`_in_memory_replay.py`, sidecar routes/models/auth, and `__init__.py`. This surfaced a large number of issues across severity levels. I prioritized fixes for the ones that affect correctness, data integrity, and security:

**High confidence fixes:**
- Silent exception swallowing → structured logging (both backends)
- HTTP connection leak → `finally` block with `try/except` close
- Missing `WHERE status = 'pending'` guard on receipt updates
- `witness_signature` stored as `Jsonb(bytes)` when it should be raw BYTEA
- Vacuous `FOR UPDATE` on autocommit connection removed
- `_parse_uuid`/`_parse_datetime` ValueError → 400 in sidecar
- InMemory `unregister_witness` cleans orphaned receipts
- InMemory `register_witness` copies headers/event_filter dicts
- InMemory replay logs halted work items

**Medium confidence fixes:**
- UNIQUE constraint on `(witness_id, event_id)` — correct pattern, but existing test data might need to be clean before the index can be created. Tests pass, so it's clean.
- `max_failures`/`max_retries` validation — the `ge=1` Pydantic constraint is correct but changes API behavior. Existing callers passing defaults are unaffected.
- URL hostname validation — added but `urlparse` on `https://` returns `hostname=None`, which now correctly raises an error.

**Not fixed (noted in breadcrumbs as proposed/accepted):**
- BC-234 (UUIDv5 SHA-1 collision risk) — low priority, UNIQUE constraint provides defense-in-depth
- BC-235 (sidecar hook endpoints lack per-hook authorization) — medium, design improvement

## On what remains

From the adversarial review, issues I chose not to fix this session:

1. **SSRF in witness delivery** (`_witness.py:314-319`) — The witness URL is used to make HTTP requests with no private IP blocking. This is a known design trade-off (witness registration requires admin). Could add a configurable allowlist/blocklist but that's a design change.

2. **`deliver_pending_receipts` N+1 query pattern** — Each receipt creates a separate DB connection/transaction for event lookup and update. At scale this will be slow. Could be batched but requires restructuring the delivery loop.

3. **Sidecar `list_witnesses` allows non-admin to see URLs and headers** — Information disclosure risk in multi-team deployments. Need role-based access control on endpoint.

4. **`update_not_before` facade doesn't validate `actor_id`** (`_ops.py:184-188`) — Inconsistency with other mutation methods. Should call `_validate_mutation_params` with `actor_id`.

5. **InMemory `_hook_id_counter` not thread-safe** — Low priority for a test backend but worth noting.

6. **`witness_receipts` grow without bound in InMemory** — No cleanup of completed/failed receipts. Memory leak in long-running tests.

## Gaps to flag

- `_witness.py:340-349` — Receipt delivery uses `mgr.connect()` (autocommit) to read events, then `mgr.transaction()` to update receipt/witness. The event read is not in the same transaction as the receipt status update — a receipt could be delivered but its event already deleted by a concurrent process, causing an infinite retry loop.
- `_witness.py:295-493` — `deliver_pending_receipts` iterates ALL active witnesses with no limit. With thousands of witnesses, this will hold connections and make N*3+ database round-trips.
- `_in_memory.py:538-564` — `claim_hooks` iterates and mutates `_hook_queue` without copying. Not thread-safe.
- `sidecar/routes.py:449` — The `limit` parameter for witness_receipts was unvalidated. Fixed to cap at 10,000, but other `limit`/`page_size` params throughout the sidecar have similar issues (e.g., `ReadEventsRequest.limit`, `QueryWorkItemsRequest.page_size`).
- `sidecar/errors.py` — Was missing 10 error code mappings. Fixed, but there's no automated test verifying that every `ErrorCode` has a mapping. A unit test should assert `set(ErrorCode) <= set(_STATUS_MAP.keys())`.
- `__init__.py:317-325` — `_try_create_witness_receipts` is called after every event-emitting mutation but operates in a separate transaction from the event insert. If receipt creation fails (now logged, no longer silent), the event exists without receipts. There's no retry mechanism. This is a design gap, not a bug — but it means the witness receipt system has at-least-once semantics at best.
- `InMemorySubstrate.witnesses` property returns `self` (the whole InMemorySubstrate instance), not a dedicated facade. This works but violates the facade pattern used by the Postgres backend.
