# Session Reflection — 2026-05-23

**Work summary:** Completed Plan 010 (delegation chain / `on_behalf_of`) across 20 source files, 1 migration, and 31 new tests. Fixed BC-199 bookkeeping and a `_recurrence.py` code-quality issue. Full suite: 802 passed, lint clean.

## On the project

Substrate is extremely mature for its scope. 802 tests, zero lint errors, a well-kept breadcrumb trail, and a spec + conventions doc that actually constrain behaviour. The code is thin façades over Postgres — which is the right choice for durability — and the InMemory backend achieves genuine parity rather than being a toy. The project has reached a point where new features are "add a column and thread it through 15 layers," which is a sign the architecture is stable.

That said, the signing layer is still homelab-grade. Plan 010 adds schema-visible delegation but does not cryptographically enforce it — `on_behalf_of` is self-attested by the caller, same as `actor_metadata`. The HMAC signature covers the field, so tampering is detectable, but there's no proof the caller was authorized by the principal they claim. That gap is acknowledged (BC-196/BC-198) and correctly deferred.

## On the work done

Plan 010 was mostly mechanical: add the parameter, validate it, thread it through every append path, update the INSERT, update `_row_to_event`, update `Event` reconstruction, update replay verification, update sidecar models. The only subtlety was the signing backward-compat: old events signed without `on_behalf_of` need a retry path in `verify_event()` when `stored_envelope` is absent. I implemented that correctly and tested it.

The `_event_store.py` `append_event()` helper missed `on_behalf_of=on_behalf_of` on the `Event(...)` constructor during the initial agent pass — that was caught by an integration test where `assert evt.on_behalf_of == ...` failed. Good reminder that even trivial dataclass construction can drift when threading a new field through 15 layers. The unit tests caught nothing because they tested signing in isolation; the integration tests caught the real bug.

I'm confident in the implementation. The one call I'd make to a future self: keep an eye on whether BC-196 (pluggable signing / Ed25519) ever lands. If it does, the `on_behalf_of` field is correctly positioned — it's already in the envelope — but the verification path will need another parameter.

## Gaps to flag

- `src/substrate/_signing.py:55-74` — The backward-compat retry in `verify_event()` duplicates the HMAC verification logic. If that logic ever changes (e.g., new hash algorithm), both branches must be updated. Consider extracting a `_verify_once` helper.
- `src/substrate/_events.py:128-136` and `_event_store.py:73-81` — `sign_event()` is called in two places with the same arguments. A shared wrapper that builds the envelope from an `Event` object would reduce duplication and drift risk.
- `spec.md` — No mention of `on_behalf_of` in the spec yet. The spec is the source of truth; it should be updated before downstream consumers start relying on the field.
- `tests/test_plan010_integration.py` — Uses `custom_fields={"title": "test"}` because the test workflow YAML requires it. This is fine, but the test is more coupled to the fixture workflow than ideal.
- `validate_delegation_chain` uses `INVALID_ARGUMENT` rather than a specific `DELEGATION_CHAIN_INVALID` error code. The Plan 010 RFC explicitly deferred adding a new code (`"If we later want specificity, we can add DELEGATION_CHAIN_INVALID without breaking changes"`). This is fine, but monitor whether consumers need it.
