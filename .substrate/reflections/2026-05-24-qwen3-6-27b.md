## On the project

Substrate is an unusually well-architected library for its stage. The core design — event-sourced with transactionally-consistent denormalized projection, schema-per-project isolation, sole-signer HMAC — is sound and consistently implemented across both Postgres and InMemory backends. The facade decomposition (Plan 007) is the structural decision that matters most: it means adding new capability domains (timestamping, recurrence, hooks) is a matter of wiring a new `*Ops` class rather than growing `__init__.py` into a god class.

The breadcrumb discipline is impressive. 200+ resolved breadcrumbs, most with concrete code changes and test additions. The few remaining open ones (BC-213) are genuinely accepted design tensions, not deferred bugs. This is a project that has been through multiple serious audits and has earned its test count.

What worries me most is **surface-area sprawl**. The sidecar routes, CLI commands, and public API methods are all thin delegates, but each one is a maintenance vector. Plans 002-012 have added significant surface area in a short span. The "no comments in code" convention, which I respect in principle, becomes harder to sustain as the codebase grows — the AGENTS.md is excellent but 8KB of context is not always available to the next agent editing `_ops.py:470`.

The dual-backend constraint (Postgres + InMemory) is both the project's greatest strength (parity is enforced by property-based tests) and its greatest source of friction. Every new feature requires two implementations, two migration paths, and conformance tests. But the `_contract.py` pure-validation layer and the `EventStore` protocol have made this manageable.

## On the work done

The changes were small and mechanical — ~70 lines across 5 files. The `list_batches` fix was the most interesting: rehydrating `event_ids` from the `events` table using the `(first_event_seq, last_event_seq)` range avoids a schema migration and a child table. It's O(n) in batch size on each `list_batches` call, but timestamping batches are expected to be infrequent reads, so the trade-off is fine. If this becomes a hot path, a JSONB column or child table is the natural evolution.

The `to_dict()` on `TimestampBatch` was necessary — the sidecar's `_serialize` relies on it, and without it, `bytes` fields (`merkle_root`, `tsa_token`) would leak as raw bytes into JSON responses. This is a pattern I'd want to audit across all dataclasses that flow through the sidecar.

The sidecar error mapping fix (`TSA_NOT_CONFIGURED` → 400) is a small correctness improvement. A missing configuration is a client error, not a server failure. The existing error map was already well-curated; this was just a late addition.

## On what remains

1. **TSA wire protocol** (`submit_to_tsa`/`verify_tsa_token`) — still `NotImplementedError`. Needs DER encoding, probably via `cryptography` or `asn1crypto`. This is the only thing preventing the timestamping feature from being end-to-end functional.

2. **Spec reconciliation for v7** — the spec revision history was updated in Session 50, but detailed sections (FR-15, §17, §19.5) should be reviewed against actual implementation. Plans 011 and 012 added significant behavior not reflected in the spec body.

3. **CLI timestamp commands** — no tests. The `cmd_timestamp_status`, `cmd_timestamp_trigger`, and `cmd_timestamp_verify` functions are untested. They're thin wrappers around `TimestampOps`, but the CLI has its own failure modes (argument parsing, stderr formatting) that deserve coverage.

4. **Ed25519 end-to-end** — the signing scheme tests pass, but there's no integration test that creates a work item, transitions it, and verifies the event with an Ed25519 key. The `test_keys_ed25519.json` file exists but may not be wired into a full lifecycle test.

## Gaps to flag

- `src/substrate/_timestamping.py:83-88` — `submit_to_tsa` and `verify_tsa_token` raise `NotImplementedError`. The public API surface (sidecar, CLI, `TimestampOps.trigger()`) will fail at runtime when a TSA config is actually provided. This is by design but creates a "works until it doesn't" situation for operators who configure a TSA URL.
- `src/substrate/_timestamping.py:185-223` — `list_batches` rehydrates `event_ids` by scanning the `events` table per batch. If there are many batches (e.g., after running timestamping for weeks), this is N+1 queries. Acceptable today; watch for performance regression.
- `src/substrate/sidecar/routes.py:387-403` — Nested REST paths (`/timestamp/batches/{id}/verify`) diverge from the sidecar's flat routing convention. Not wrong, but if the sidecar grows, a routing convention should be documented.
- `src/substrate/_cli.py` — No tests for the timestamp CLI subcommands. The CLI has 10+ commands and zero integration tests. A single smoke-test fixture that runs `substrate workflow validate` and checks exit codes would catch argument-parsing regressions.
- `src/substrate/sidecar/models.py` — `_serialize` handles `bytes` → hex, but this was not sufficient for `TimestampBatch` without `to_dict()`. Audit whether other dataclasses that flow through the sidecar (e.g., `ReplayReport`, `RecurrenceRule`) have the same gap.
