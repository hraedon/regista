# Session Reflection — 2026-06-26

**Work summary:** Conducted an in-depth code review of the regista project, fixing 8 code-level issues (heartbeat_claim actor_kind, replay None global_seq, sidecar dead-letter limit, routes_hooks infinite loop, InMemory start_maintenance parity, dead code, sign_secret exposure) and 2 high-severity architectural issues (BC-314: timestamping transaction held during HTTP, BC-315: stuck witness receipts). Added 19 new tests across coverage gaps and maintenance thread behaviors. Two rounds of adversarial review from Kimi addressed 12 additional findings. Tagged v0.5.1-rc1, CI green on 3.11/3.12/3.13.

## On the project

Regista is mature — 1273 tests, 316 breadcrumbs tracked, Plans 002-022 all implemented. The codebase is well-structured with clear separation between the Postgres and InMemory backends, and the `_contract.py` single-source-of-truth pattern is working well for parity. The breadcrumb system provides excellent traceability.

The main weakness I see is in the "external I/O during database transaction" pattern. Both BC-314 (timestamping) and BC-315 (witness receipts) had the same root cause: holding a DB transaction open while making HTTP calls. This pattern likely exists elsewhere too — any code path that does `with mgr.transaction() as conn:` followed by network or file I/O is a latent connection-pool exhaustion risk. A lint check or architectural review for this anti-pattern would be worthwhile.

## On the work done

The in-depth review was effective — the two-agent approach (general reviewer for code + explore agent for test gaps) surfaced issues I wouldn't have found by reading code alone. The adversarial review (Kimi) caught subtle issues I missed: the `not` vs `is None` check, the sidecar using `body.actor_kind` instead of `actor.actor_kind`, and the Phase 3 race condition in timestamping.

The timestamping transaction split was the most complex change. The key insight from adversarial review was that the Phase 3 UPDATE needed a `WHERE status = 'pending'` guard to prevent the stale sweep from racing with confirmation. This was a genuine correctness concern that would have been a latent bug in production.

The maintenance thread tests were straightforward but valuable — 6 of 7 behaviors had zero integration coverage. The tests use `time.sleep()` which makes them slow (75s for the full test file), but the alternative (mocking the thread) would defeat the purpose of integration testing.

I'm confident in all the fixes. The one area I'd want a second pair of eyes on is the `sweep_stale_timestamp_batches` function — the `make_interval(secs => %s)` approach works in Postgres but I haven't verified it works correctly for very large values (overflow at ~2^63 seconds, which is academic but worth noting).

## On what remains

- **BC-312**: InMemory witness delivery has no concurrency lock. Still proposed.
- **BC-313**: Sidecar hook authorization TOCTOU. Still proposed.
- The maintenance thread tests are slow (75s). If this becomes a problem, consider running them in a separate CI job or using a mock clock.
- The `v0.5.1-rc1` tag is pushed but not a final release. After promoting to `v0.5.1`, update the version in `pyproject.toml`.

## Gaps to flag

- `src/regista/_timestamping.py:502` — Event selection doesn't exclude events already covered by pending batches (BC-316). Concurrent callers will duplicate TSA submissions.
- `src/regista/_in_memory.py:1214` — `sweep_stale_timestamp_batches` is a hard-coded no-op returning 0. Acceptable since InMemory has no timestamping, but the public API advertises parity.
- `tests/test_plan009.py:615` — `TestMaintenanceMetricsRefresh` doesn't actually assert on metric values, only `last_cycle_ok`. Weak test.
- `src/regista/_witness.py:439` — `deliver_pending_receipts` still marks receipts `in_progress` in one transaction then delivers outside any transaction. The sweep (BC-315) is a recovery mechanism, but the fundamental pattern of "mark in_progress → deliver outside txn → update" still has a window where a crash leaves receipts stuck. The sweep mitigates but doesn't eliminate this.
- `src/regista/_maintenance.py` — The `_run` loop calls 9 operations sequentially. If any is slow (e.g., witness delivery with 10s timeout), it delays all subsequent operations. Consider a thread pool or separate timers for independent concerns.
