## On the project

Regista is at a mature state — 1255 tests, 296 resolved breadcrumbs, 5 open (3 accepted design tensions, 2 newly proposed medium bugs). The codebase is well-organized with clear separation between contract logic (`_contract.py`), storage layers (`_events.py`, `_event_store.py`, `_in_memory_events.py`), and API facades. The breadcrumb culture is strong and genuinely useful — every issue has context, severity, and resolution notes.

The signing envelope system (v1-v4) is the most complex area. BC-308's version filtering and BC-311's chain field forwarding are both attempts to make verification more robust without breaking backward compatibility. The spec audit caught a real issue: the BC-311 breadcrumb suggested forwarding `global_seq` but spec §17.11 says it's post-signing and NOT in the envelope. This is exactly the kind of spec-vs-implementation drift that a breadcrumb author (an adversarial reviewer) can introduce when they don't have full spec context.

The InMemory backend is the recurring parity defect class (42+ resolved breadcrumbs). BC-307 closes the last major gap (witness delivery), but the lack of concurrency safety (BC-312) is a natural consequence of InMemory being a dict-based test backend — it's not designed for concurrent access, yet `start_maintenance()` creates a thread that could overlap with manual calls.

## On the work done

**What went well:**
- Parallelizing BC-235 and BC-307 as subagent tasks saved significant time. Both subagents produced working implementations that passed tests.
- The spec audit was high-value: it caught the `global_seq` issue that would have been a subtle correctness bug. The breadcrumb's suggestion seemed reasonable but contradicted the spec.
- Cross-model adversarial review caught real issues: GLM found the stuck `in_progress` hooks (C1) and empty-list = unrestricted (C2) in BC-235; Kimi found the Ed25519 verification gap in BC-307.

**What was awkward:**
- The `_events_api.py` import block was fragile — my no-op edit somehow corrupted a closing `)`. The file had a complex multi-block import structure that's easy to break. This should be consolidated into a single import block.
- The InMemory test for BC-311 required knowledge of `InMemoryEventStore`'s internal structure (`self.events` is a `dict[UUID, list[Event]]`, not a flat list). The `_testing` module doesn't expose a clean way to mutate stored events for test scenarios.

**What I'm confident in:**
- BC-311: The fix is correct and the regression tests prove it. The spec audit correction (not forwarding `global_seq`) is well-grounded in §17.11.
- BC-306: Straightforward centralization, all paths covered.
- BC-294: Test hygiene fix follows established pattern from `test_migration_safety.py`.

**What I'd want a second pair of eyes on:**
- BC-235's `_release_hook()` helper: it directly manipulates the InMemory `_hook_queue` dict and runs raw SQL for Postgres. This is reaching into internals. A public `release_hook()` method on `Regista`/`InMemoryRegista` would be cleaner but is scope creep.
- BC-307's Ed25519 verification: I added it to match Postgres parity, but I couldn't write a test for it because the test infrastructure doesn't have Ed25519 witness key setup in InMemory. The code path exists but is untested.
