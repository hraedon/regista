# Session Reflection — 2026-06-23

**Work summary:** Implemented Plan 022 Phase 2 (crypto-agility: kill scheme allowlist,
hash_alg agility, hybrid seam, size audit) and Phase 4 (cross-project value-references
with typed links). Three rounds of adversarial review (glm-based) caught a critical
remove_link filtering bug, a chain hash mismatch, and several parity gaps. Spec
amended for FR-22b. 1140 tests pass, lint clean.

---

## On the project

Regista's architecture is well-suited for the crypto-agility evolution. The
`SigningScheme` protocol + registry pattern is clean — adding a new scheme is
a decorator + optional dependency, no envelope bump needed. The entity
generalization from Phase 1 (entity_kind/entity_id) makes the cross-project
value-reference model natural: a link event already binds to an entity, so
adding `target_project` is a payload extension, not a schema change.

The spec's isolation tenet (§3) is load-bearing and the adversarial review
process around it was the right call. The value-reference design — "like a URL,
not a foreign key" — is elegant and preserves isolation by construction. No
cross-schema query, no FK, no transaction. The signed assertion is
non-repudiable. This is the right model for federated agent workflows.

One thing that feels fragile: the `_links.py` live-link query is complex SQL
with a `NOT EXISTS` subquery. Adding the `target_project` filter with
`IS NOT DISTINCT FROM` made it more complex. This is correct but hard to read.
A future simplification could materialize current links into a table.

## On the work done

**What went well:**
- The adversarial review process was extremely valuable. The P2 review caught
  a critical chain hash mismatch (write path used sha-256, replay used
  event's hash_alg) that would have caused false chain-breaks when non-sha-256
  hash_alg is used. The P4 implementation review caught a critical bug where
  `remove_link` didn't filter by `target_project`, making multiple cross-project
  links to the same UUID indistinguishable. Both were latent — they wouldn't
  have surfaced until someone actually used a non-sha-256 hash or created
  multiple cross-project links to the same target.

**What I'm confident in:**
- The registry-driven scheme resolution is clean and correct. The
  `resolve_hash_function` utility is simple and well-tested.
- The cross-project value-reference design preserves isolation by construction.
  No cross-schema coupling exists in any code path.
- The spec amendments are precise and match the implementation.

**What I'd want a second pair of eyes on:**
- The `IS NOT DISTINCT FROM` SQL in the live-link query — I'm confident it's
  correct but the semantics of NULL comparison in JSONB `->>'key'` (returns
  NULL when key absent) vs SQL NULL (when `target_project` parameter is None)
  is subtle. The test `test_multiple_cross_project_links_same_target_distinct`
  covers it, but more edge cases would be welcome.
- The decision to always use sha-256 for chain hash verification (decoupled
  from signing hash_alg) — this is simpler but deviates from the plan's
  wording ("prev_event_hash = hash_alg(...)"). The plan should be amended
  to note this design choice.

## On what remains

**Needed before this can ship to production:**
1. Plan 022 Phase 3 — per-principal asymmetric adoption (BC-216/217). This is
   the operational adoption of Ed25519 keys: key→principal resolution,
   revocation, dossier/agent-provenance opt-in. HMAC remains default.
2. BC-298 — PostgresEventStore.append() omits prev_global_event_hash from
   INSERT. This is a data integrity bug in the EventStore path.
3. BC-299 — Spec still not updated for Phase 1 (envelope v4 shape, entity
   columns). The spec describes v3 envelopes. I amended for Phase 4 but
   the Phase 1 amendment is still needed.

**Nice to have:**
4. BC-300 — Global chain hash not verified during replay (defense-in-depth gap)
5. BC-301 — content_hash has no size limit (resource exhaustion risk)
6. InMemory `links` list doesn't store `target_entity_kind` or `content_hash`
   (incomplete projection, no current consumer reads these fields)
7. The `HMACSHA256Scheme` name is misleading after hash_alg agility — it
   supports any hash algorithm now. Consider renaming to `HMACScheme`.

## Gaps to flag

- **`_links.py:228-249`**: The live-link query with `IS NOT DISTINCT FROM`
  for `target_project` is correct but complex. Any future change to the
  link matching logic must keep the `target_project` filter in sync across
  both the main query and the `NOT EXISTS` subquery.
- **`_signing.py:59-70`**: Dead code — `compute_hmac`, `compute_canonical_hash`,
  `verify_hmac` are not called anywhere. They use hardcoded sha-256. Should
  be removed or updated.
- **`_signing.py:236-240`**: `classify_envelope_version` has a redundant V4
  check — the first `if` (with `prev_event_hash`) is a subset of the second.
  Dead branch.
- **`_signing_scheme.py:148-154`**: `Ed25519Scheme.verify` catches broad
  `Exception` and returns `False`. Unexpected errors during verification
  should propagate to the replay error handler, not be silently swallowed.
  Pre-existing but worth fixing.
- **`spec.md`**: The plan says "prev_event_hash = hash_alg(...)" but the
  implementation uses sha-256 for chain hashes regardless of the event's
  hash_alg. This design choice (decoupling chain integrity from signing
  hash) should be documented as a plan amendment or spec note.
- **`_in_memory_links.py:111-118`**: The `links` list stores `target_project`
  but not `target_entity_kind` or `content_hash`. No current code reads
  these from the list, but it's an incomplete projection.
