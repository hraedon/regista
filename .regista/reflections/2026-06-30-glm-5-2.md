# Session Reflection — 2026-06-30

**Work summary:** Implemented Plan 024 — investigated global hash chain
breakage reported across 14 of 15 production schemas. Phase 0 determined it
was a verifier bug (not data corruption): the replay verifier sorted events
by `global_seq` (which diverges from append order under CACHE 100) instead
of walking the chain by `prev_global_event_hash` links. Fixed the verifier
to walk by hash links, hardened the append path with `CACHE 1` (migration
034), and added 6 regression tests. All 11 production schemas re-verified
clean.

---

## On the project

Regista's global hash chain is its store-level tamper-evidence anchor (G2).
The design is sound — migration 030's comment even says "a hash walk that is
immune to global_seq gaps" — but the implementation betrayed the design by
sorting on `global_seq` instead of walking. This is a classic
spec-vs-implementation gap: the comment described the right approach, the
code did the wrong thing, and nobody caught it because the tests didn't
exercise concurrent appends at the global-chain level.

The CACHE 100 issue is a subtle Postgres behavior that's easy to miss. The
sequence's `CACHE 100` is a performance optimization for high-throughput
workloads, but regista is an agent-pipeline coordinator, not a
high-throughput event bus. `CACHE 1` is the right tradeoff — negligible
performance impact, and it makes `global_seq` a reliable total order that
matches append order.

The investigation-first design of Plan 024 was the right call. The plan
explicitly warned: "do not accept a repair plan that skips Phase 0." Had we
jumped to Phase 3 (data repair), we'd have rewritten `prev_global_event_hash`
values that were already correct, potentially corrupting the chain. The
plan's two-signature analysis (windowed vs from-seq-2) was also prescient —
both patterns had the same root cause, but the uniformity of the from-seq-2
pattern was the key signal that pointed to a systematic computation issue
rather than a race condition.

## On the work done

The investigation was the highest-value part of this session. The
manual-recompute script (`/tmp/opencode/phase0_manual_recompute.py`) was
straightforward but decisive — it showed that the stored
`prev_global_event_hash` values were valid SHA-256 hashes, just chained to
the "wrong" predecessor in `global_seq` order. The chain-walk script
(`/tmp/opencode/phase0_chain_walk.py`) confirmed the chain was intact
across all schemas.

The verifier fix itself was clean — replacing the sort-and-check loop with a
hash-walk that builds a `link_map` and traverses from genesis. The trickiest
part was handling events with NULL `canonical_envelope` (the BC-311 test):
the old code only warned when computing a NULL-envelope predecessor's hash
for a successor, so the tail event with NULL envelope produced no warning.
The new code needed to `break` (not warn) when the current event has NULL
envelope, treating it as the chain tail — matching the old behavior while
still detecting orphans.

The `CACHE 1` migration was a one-liner. The key insight was that the append
path already calls `nextval` AFTER acquiring the `FOR UPDATE` lock, so with
`CACHE 1` the values are guaranteed to be in lock-acquisition order. No code
changes needed in the append path — just the sequence cache change.

The regression tests cover both the verifier (concurrent appends replay
clean, orphan/cycle detection) and the append path (global_seq matches chain
order with CACHE 1). The concurrent test using `ThreadPoolExecutor` with 10
workers × 3 transitions was sufficient to reproduce the interleaving that
would have broken the old verifier.

One thing I'm slightly uncertain about: the genesis case (empty
`event_chain_head` table). When the table is empty, `SELECT ... FOR UPDATE`
returns nothing immediately — no row to lock. Two concurrent transactions
could both see an empty table and both get `prev_global_event_hash = NULL`
(two genesis events). This is a pre-existing issue, not introduced by my
change, and it's extremely rare (only the very first events in a fresh
schema). The new verifier would warn about multiple genesis, which is
correct behavior. But it's not tested.

## Gaps to flag

- **Genesis race condition** (`_events.py:_lock_global_chain_head`): When
  `event_chain_head` is empty, `SELECT ... FOR UPDATE` returns nothing — no
  serialization. Two concurrent first-events could both get
  `prev_global_event_hash = NULL`. Pre-existing, extremely rare, not tested.
  Consider initializing `event_chain_head` with a row in migration 030 (or a
  future migration) so `FOR UPDATE` always has a row to lock.
- **`global_seq` not in signed envelope** (`_signing.py:sign_event`):
  `global_seq` is not passed to `sign_event`, so it's not in the signed
  envelope. This is by design (the envelope signs the link, not the
  position), but it means `global_seq` can be changed without invalidating
  the signature. The hash chain provides integrity; `global_seq` is just a
  convenience ordering key. This is fine, but worth being explicit about.
- **The `test_replay_no_drift` smoke test** (`tests/test_smoke.py`) has been
  failing for at least one session with `WORKFLOW_NOT_REGISTERED`. It's a
  fixture issue, not a code issue, but it means the smoke test isn't
  providing coverage.
- **Two append paths** (`_events.py` vs `_event_store.py`): The codebase
  has two separate append implementations — the original Postgres path
  (`_events.py:append_event` / `append_transition_event`) and the newer
  shared path (`_event_store.py:append_event` + `PostgresEventStore.append`).
  Both compute the head hash and advance the chain, but they're independent
  code. The `CACHE 1` fix works for both (since both call `nextval` via the
  DEFAULT), but future changes to the chain logic need to be applied to
  both. BC-183 was supposed to decompose these; the duplication is a
  lingering risk.
