# Session Reflection — 2026-05-25

**Work summary:** Adversarial review of the full regista codebase (core library, sidecar, CLI, migrations). Found and fixed 13 issues across BC-244–BC-256: TOCTOU in witness delivery, double metric counting, unhandled exceptions, missing validation, sidecar security hardening (auth, docs, bind address), InMemory parity gap, and missing database constraints.

---

## On the project

The codebase is remarkably consistent for its size. The breadcrumb trail (256 items and counting) is a genuine asset — being able to trace every design decision and bug fix through BC-numbered entries gives the code an unusual level of historical context. The convention of no comments in code is well-maintained and the spec-first approach is real, not aspirational.

The main fragility I see is the witness delivery system (`_witness.py`). It's the newest subsystem and it shows — the TOCTOU fix (BC-244) was the most complex change this session, and there are still open concerns around SSRF (no private IP blocking in `_validate_url`) and the async sidecar handlers blocking the event loop. These are both known (BC-235 for auth, and the sidecar async issue was flagged but not filed as a BC). The witness system needs another hardening pass before it's production-ready for untrusted environments.

The InMemory backend continues to be a source of parity gaps. BC-255 (missing `next_retry_at` filter) is the latest in a long series. The property-based conformance tests (RFC-062) help, but they don't cover every filter predicate. A systematic audit of all Postgres WHERE clauses against InMemory list comprehensions would be valuable.

## On the work done

The three-agent parallel scan (core, sidecar, migrations) worked well for coverage. The migration reviewer found the CHECK constraint issues which would be invisible in code review. The sidecar reviewer caught the `allowed_roles` mutability issue which is a latent privilege escalation vector.

One false alarm worth noting: the heartbeat coalesce threshold at `_claims.py:225` was initially flagged as comparing "wrong values" (`new_expires_at - last_emitted` vs `now - last_emitted`). On closer inspection, `last_heartbeat_emitted_at` stores the previous `new_expires_at` (= `prev_now + ttl`), so the `ttl` terms cancel out and the comparison correctly measures elapsed wall-clock time. This was caught before committing but illustrates the danger of surface-level "obvious bug" analysis on coalescing logic.

The migration 022 is the riskiest change — adding CHECK constraints to tables that may have existing data. If any existing rows have invalid status values, the ALTER TABLE will fail. In practice this is unlikely since the app code has always used valid values, but it's worth noting.

## On what remains

**Before production witness deployment:**
1. SSRF mitigation in `_validate_url` — block RFC 1918, loopback, link-local, and cloud metadata ranges
2. Sidecar async handlers should be `def` (not `async def`) to get automatic threadpool offloading from FastAPI
3. Document at-least-once delivery semantics for witness receipts

**Nice-to-have:**
- `validate_json_safe_value` recursion depth limit (M-08 from core scan)
- Server-side cursor for replay event loading (L-07 from core scan)
- `register_recurrence_rule` workflow existence validation (M-06 from core scan)
- `_find_next_future_slot` already fixed in closed form, but recurrence edge cases deserve more property-based testing

## Gaps to flag

- **SSRF in witness URL registration** (`_witness.py:17-29`): `_validate_url` does not block private IPs. Admin-only endpoint mitigates this, but in multi-admin environments it's still exploitable. Should be BC'd.
- **Sidecar async handlers block event loop** (`routes.py` all handlers): Every handler is `async def` but calls synchronous psycopg I/O. Under load, a single slow query blocks ALL concurrent requests. Not yet filed as BC.
- **`trigger_timestamping` holds transaction during TSA HTTP call** (`_timestamping.py:223-315`): 30-second TSA timeout holds a pool connection. Should split into batch-creation + out-of-transaction HTTP + status-update. Not yet filed.
- **`_serialize` recursion without depth limit** (`sidecar/models.py:10-25`): User-controlled custom fields could cause RecursionError. Low probability but no guard.
- **Migration 022 CHECK constraints**: If existing data has invalid status values, migration will fail. Should be validated on a staging copy first.
