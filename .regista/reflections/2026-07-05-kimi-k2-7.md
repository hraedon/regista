## On the project

Regista is holding together well, but the boundary between the legacy keyset and the new principal-key registry is still fuzzy. The keyset is a file of signing secrets; the principal registry is a DB table of public keys. For non-repudiation to be real, the event's `key_id` must resolve in *both* — the keyset proves the signer had the secret, the registry proves the secret belongs to that actor. The code now enforces that link for asymmetric schemes, but the HMAC path still has a fallback that accepts any active keyset key. That's probably correct for backward compatibility, but it means HMAC-only deployments are not getting principal-binding guarantees.

The other tension is key-rotation UX: `rotate_principal_key` generates a fresh `pk_*` key_id that is not automatically present in the keyset, so the next event will be signed with whatever keyset key is still active — often an older, now-superseded principal key. This produces a valid signature that fails the new temporal check. That's the *right* security answer, but the developer experience is confusing: rotation currently requires manually updating the key file with the new `pk_*` entry or accepting that events after rotation are rejected. A production rotation flow should probably rotate the keyset and the registry in one step, or `resolve_signing_key` should look up the active principal key and fail loudly if it has no matching keyset entry.

## On the work done

The core change — `_verify_principal_binding_core` — is clean and shared between runtime verification and replay. I like that it now returns distinct failure states (`key-id-mismatch`, `key-not-valid-at-time`) and that the temporal check is fail-closed when the timestamp is missing.

I am less confident about `KeySet._latest_active_key_for`: it picks the last asymmetric candidate in JSON order. That is a heuristic, not a semantic rule. The fixture tests now rely on ordering v1 before v2 to get the right behavior. If a user lists keys in a different order, the signer may pick an unexpected key. The *correct* behavior is probably to query the active principal key and match by key_id, but that would require plumbing a `ConnectionManager` into `KeySet.resolve_signing_key`, which is a bigger refactor. For this session, the heuristic is acceptable because it unblocks the gap fixes, but it should be revisited before the rotation UX is documented as production-ready.

The tests I added are adversarial and exercise the temporal and key-id-mismatch paths. They caught the ordering issue and the rotation mismatch, which is exactly what they were for. I would want a second pair of eyes on whether the HMAC fallback in `_verify_principal_binding_core` is too permissive — currently it does not reject an unknown `key_id` if `scheme_id == "hmac-sha256"`, because HMAC deployments may not have a principal registry at all.

## On what remains

- **Production-ready rotation:** Make `resolve_signing_key` either look up the active principal key or at least fail loudly when the keyset's active key does not match the registry's active key. This needs a design decision.
- **HMAC principal binding:** Decide whether HMAC-only deployments should get any binding guarantees, or whether they are explicitly out of scope for Plan 026.
- **Global chain hash verification:** BC-300 / Plan 024 added chain hash fields but the global chain hash (`prev_global_event_hash`) is still not verified during replay. Open work item 300.
- **Slow property tests:** `test_random_sequences_equivalent` is flaky and fails on some Hypothesis seeds with `last_event_seq` mismatch after sweep operations. This looks pre-existing and unrelated to binding changes, but it is noisy and should be investigated.

## Gaps to flag

- `src/regista/_keys.py:279` — `_latest_active_key_for` uses JSON order as a proxy for "latest." Flagged above; should be replaced with a registry-aware lookup.
- `src/regista/_signing.py:547` — HMAC events bypass the `key-id-mismatch` check. Intentional for backward compatibility, but should be documented in the spec if it is not already.
- `tests/test_signer_binding.py` — the rotation tests rely on the keyset file ordering v1 before v2. If the fixture ordering changes, tests will pass but exercise the wrong path.
- `tests/test_property_conformance.py` — `test_random_sequences_equivalent` fails on seeds 1 and 6 with sweep-related `last_event_seq` drift. This is pre-existing flakiness but makes the slow suite non-deterministic.
- `src/regista/_replay.py:712` — `UndefinedTable` now warns and counts, which is correct, but the empty cache means every subsequent event for that actor re-logs the warning. Consider caching the "missing table" state for the rest of the replay run to avoid log spam.
