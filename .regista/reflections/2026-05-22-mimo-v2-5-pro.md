# Session Reflection — 2026-05-22

**Work summary:** Adversarial review of the Regista codebase and its consumers (SF2, compliance-regista, agent-provenance). Filed 12 new breadcrumbs (BC-199 through BC-210) covering security gaps, null-check defects, misleading health signals, and test coverage holes. No code was modified.

---

## On the project

Regista is the best-engineered component in this constellation. The `_contract.py` pattern — 20 pure functions as single source of truth for both Postgres and InMemory backends, verified by property-based tests — is genuinely elegant. The 192 resolved breadcrumbs with zero open items before this session is unusual discipline. The spec is honest about trade-offs. The `InMemoryRegista` for testing is a killer feature.

The core architecture (event-sourced with transactionally-consistent projection) is the right model. The signing, canonicalization, and key management are well-implemented for the homelab scope. The facade decomposition (Plan 007) and trust hardening (Plan 008) show the codebase maturing without over-engineering.

What feels fragile: the edges are rougher than the core. The sidecar auth model is permissive-by-default, which is backwards for a security boundary. The claim lifecycle has null-check gaps that could silently corrupt state. The hook consumer can stop processing while reporting healthy. The recurrence system has zero Postgres tests despite being the exact pattern that caused the Session 11-14 bug flood. These are all fixable, but they suggest Regista is "production-ready for the happy path" rather than "production-ready for adversarial conditions."

What feels wrong: the `InMemory/Postgres parity` problem is structural. 30+ resolved breadcrumbs are parity bugs. The `_contract.py` extraction helped, but recurrence operations bypass the contract entirely (they have their own SQL). Every new feature risks reintroducing this class of bug. The test suite needs a systematic approach to parity verification, not just ad-hoc conformance tests.

## On the work done

This was a pure review session — no code changes, just analysis and breadcrumb filing. The three parallel exploration tasks (core codebase, tests/breadcrumbs, consumers) gave good coverage. The adversarial framing was useful: asking "what breaks under contention?" and "what silently fails?" surfaced issues that a normal review would miss.

The most useful findings were the ones that surprised me:
- `initiative.py` and `review_surface.py` in SF2 calling non-existent API methods — this means there's dead code that would crash at runtime, and tests are masking it by mocking Regista
- The hook consumer's `is_running` lying after connection exhaustion — this is a real operational blind spot
- `validate_yaml` reading files by path — a confused-deputy issue I wouldn't have found without thinking like an attacker

What I'm less confident in: the sweep race condition (BC-202). The BC-114 fix does mitigate it, and I described a narrow window that might not be practically exploitable under normal load. I flagged it as high severity because the code pattern is inherently racy, but under homelab scale it's probably fine.

## On what remains

The 12 breadcrumbs I filed are all real, but they're not equally urgent:

**Before any multi-tenant or external deployment:**
1. BC-199 (sidecar auth) — must fix before exposing to untrusted networks
2. BC-201 (null-check in heartbeat/release) — silent data loss
3. BC-204 (dead-letter audit trail gap) — compliance risk

**Before production hardening:**
4. BC-202 (sweep race) — add row-level re-verification after lock
5. BC-203 (is_running lies) — track processing state separately
6. BC-207 (maintenance_healthy misleading) — distinguish never-started from crashed
7. BC-200 (validate_yaml file confusion) — remove auto-detection

**Before feature expansion:**
8. BC-210 (recurrence Postgres tests) — highest regression risk
9. BC-209 (replay test coverage) — many untested derivation paths

**Nice to have:**
10. BC-205 (input validation) — harden actor_id, role
11. BC-206 (synchronous_commit on hook consumer) — enforce spec guarantee
12. BC-208 (P1M = 31 days) — document the behavior

For SF2 specifically: the broken `initiative.py` and `review_surface.py` need to be fixed or removed. The missing heartbeat on long claims is a production time bomb. These aren't Regista bugs — they're consumer bugs — but they'll cause real problems.

## Gaps to flag

- **BC-202 (sweep race):** I may have over-stated the severity. The BC-114 `WHERE claimed_by = %s` guard handles the common case. The window I described (concurrent acquire not yet committed) requires the sweep and acquire to overlap within milliseconds. Under homelab load, this is unlikely. I kept it as "high" because the code pattern is inherently racy, but a pragmatic triage might downgrade it.
- **BC-209 (replay tests):** The property-based conformance tests DO verify replay equivalence, which catches many classes of bugs. The specific derivation paths I listed (claim_stolen, escalated, etc.) are real gaps, but the conformance tests provide a safety net. The risk is a bug in a specific derivation path that doesn't cause drift in the fields the conformance test checks.
- **SF2 consumer analysis:** I only explored the files I could find. There may be more broken API calls in files I didn't read. The `initiative.py` and `review_surface.py` findings suggest a pattern of writing against a planned API — there could be more.
- **agent-provenance:** I couldn't evaluate this meaningfully because there's no code. The design document references BC-196 and BC-197 (asymmetric signing, delegation chain) which are in the resolved breadcrumbs but marked as "accepted — deferred." The project is blocked on features that don't exist yet.
