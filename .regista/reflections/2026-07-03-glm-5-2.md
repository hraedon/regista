## On the project

Regista's architecture is maturing well. The event-sourced model with the projection table is solid, and the facade decomposition (Plan 007) keeps the public API clean. The Plan 025/026 work adds the deployment surface (provisioning, config, secrets, doctor) and the non-repudiation layer (per-principal Ed25519 signing) that the suite needs for multi-user production.

The key file format is the load-bearing interface between provisioning and signing — `secret_ref` support in `KeySet._load()` is the bridge that makes per-principal signing real (private keys in the secret backend, not embedded in the key file). This is a good design: the key file is a manifest of *what* keys exist and *where* their secrets live, not a container for the secrets themselves.

The codebase's convention of no comments (style rule) works well here — the code is self-explanatory through naming and structure, and the spec/AGENTS.md carries the intent.

## On the work done

**What went well:**
- The provision implementation was straightforward — create schema, run migrations, create service role, grant privileges. The idempotency (no-op on re-run) is clean.
- The signer binding verification logic is the heart of WI-1.2. The adversarial review caught that the initial approach (look up active key by actor_id) would break after rotation — old events signed with the superseded key would fail verification. The fix (try all non-revoked keys) is correct and handles rotation properly.
- The `secret_ref` support in KeySet was a small change (8 lines) that unblocks the entire per-principal signing path. The `provision-principal` command generates the keypair, writes the private key to disk, and adds a key file entry with `secret_ref: "file:/path/to/key"`.
- 18 focused tests cases cover provision (schema/role creation, idempotency, dry-run, cross-schema denial), provision-principal (keypair issuance, idempotency, dry-run), signer binding (matching principal, unregistered signer, scheme mismatch, key rotation historical verification, path traversal rejection), and secret_ref (file, env providers).

**What I'm confident in:**
- The provision + service role creation is well-tested with real Postgres.
- The signer binding verification handles the rotation case correctly.
- The path traversal prevention is solid (regex validation on principal_id).
- The atomic key file write (temp + os.replace) prevents corruption.

**What I'd want a second pair of eyes on:**
- The `verify_event_with_principal_binding` function tries all non-revoked keys for the actor. This is O(n) in the number of keys per principal. For a principal with many rotations, this could be slow. A key_id→public_key lookup would be faster, but the key file's key_id and the registry's key_id are different namespaces — there's no direct mapping. A future improvement could register the key file's key_id in the principal_keys registry.
- The `_provision.py` module's `_revoke_cross_schema` function iterates all schemas and revokes privileges. This is a defense-in-depth measure but could be slow with many projects. It's idempotent and safe, just not fast.
- The `provision_principal` function writes the private key as raw bytes to disk. The plan mentions storing it in the "secret backend" — the current implementation uses `file:` by default, which is the simplest backend. Vault/Azure support is available through `secret_ref` but `provision-principal` doesn't yet support specifying a non-file backend. This is a reasonable v1 limitation.

## Gaps to flag

- **`provision_principal` doesn't update the key file when `already_existed=True`** — if a principal's key exists in the DB but not in the key file (e.g., registered via `principal register` CLI), `provision-principal` returns `already_existed` without syncing the key file. The key file becomes stale. (`src/regista/_provision.py:287-299`)
- **No file locking on the key file** — `provision_principal` uses atomic write (temp + rename), but there's no `flock` to prevent concurrent `provision-principal` calls from racing on the read-modify-write cycle. The atomic write prevents corruption but the last writer wins. (`src/regista/_provision.py:344-386`)
- **Private keys stored in plaintext** — Ed25519 private keys are written as raw bytes to `principal_id_ed25519.key`. No encryption at rest. The `secret_ref: file:` mechanism references this plaintext file. If the filesystem is compromised, all principal keys are exposed. (`src/regista/_provision.py:308-313`)
- **No timeout on secret resolution** — Vault/Azure providers make network calls with no timeout. A network partition blocks `KeySet` initialization indefinitely. (`src/regista/_secrets.py:84-98`)
- **`agent-notes reconcile` fails** — the `reconcile --apply` command crashes with `ValueError: Unsupported status transition: 'in_review' -> 'closed'`. This is an agent-notes bug, not a regista bug, but it means work items can't be auto-reconciled. (agent-notes project)
- **`_revoke_cross_schema` is O(n) in total schemas** — iterates all non-reserved schemas to revoke privileges. Acceptable for homelab scale but won't scale to hundreds of projects on one DB. (`src/regista/_provision.py:124-139`)
- **Replay doesn't use principal binding verification** — `verify_event_with_principal_binding` exists as an API but the replay path (`_replay.py:649`) still uses `verify_event` directly. Events signed by per-principal keys are verified against the key set's public keys, not the principal_keys registry. This means replay doesn't catch actor↔signer mismatches. (Plan 026 WI-2.2 will fix this.)
