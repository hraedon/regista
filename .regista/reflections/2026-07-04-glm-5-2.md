# Session Reflection — 2026-07-04

**Work summary:** Implemented two plan items in a single commit: Plan 026 WI-2.2 (replay principal binding — `replay(verify_principal_binding=True)` verifies each event's signature against the principal_keys registry) and Plan 025 WI-4.3 (spec.yaml as a signed founding artifact — `sign_spec()` stores spec content as a signed `entity_kind="spec"` event). Both went through adversarial review (two independent reviewers), and 6 review findings were fixed before commit.

---

## On the project

Regista's entity generalization (Plan 022) continues to pay dividends. Adding "spec" as a new entity kind required zero schema changes — the existing `entity_kind`/`entity_id` columns, advisory locking, and hash chain all work transparently. The `_ALLOWED_ENTITY_KINDS` set in `_contract.py` is the single gatekeeper, which is exactly the right design.

The replay code is getting complex. `_replay_inner` in `_replay.py` is now ~200 lines with orphan detection, global chain verification, timestamp verification, and principal binding verification all interleaved. The per-work-item loop in `_replay_work_item` is similarly growing. This isn't broken yet, but it's approaching the point where extraction into separate verifier modules would help readability.

The dual-backend pattern (Postgres + InMemory) is well-maintained but creates a real maintenance cost. Every new feature requires parallel implementation in `_api_meta.py` + `_in_mem_workflow.py`, and the InMemory `read_spec_events` bug (truncating at 10k events) shows how easily the two backends can diverge.

## On the work done

**WI-2.2 (replay principal binding):** The core design — refactoring `_verify_principal_binding_core` as a shared function with a `verify_fn` callback — is clean. The dict-based `verify_event_dict_principal_binding` is necessary because replay works with raw DB rows, not Event dataclasses. The adversarial reviewer flagged that exceptions from `verify_event` could halt the work item instead of just warning; this was fixed by wrapping `_verify_with_key` in try/except.

What I'm confident in: the test coverage for the headline attack (forged actor with victim ID) is solid. The backward-compatibility path (no principal keys → skip) works correctly.

What I'm less confident in: the `psycopg.errors.UndefinedTable` catch in the replay path. The reviewer flagged this as a potential silent bypass — if the `principal_keys` table is dropped, all binding checks are silently skipped. This is a design tradeoff for backward compat with pre-038 schemas, but it's a real risk. The reviewer also flagged that `valid_from`/`valid_to` are ignored — superseded keys can verify events outside their validity window. This is a known gap that should be addressed in Plan 026 WI-3.1 (rotation/revocation lifecycle).

**WI-4.3 (spec entity):** The implementation is minimal and correct — regista stores and signs the spec without parsing it, which is exactly what the plan calls for. The `known_spec_schema_versions` parameter defaults to empty (all versions flagged), which is conservative but correct since regista doesn't own the spec schema.

The sidecar actor impersonation vulnerability (H-1) was caught by the adversarial reviewer — the initial implementation took `actor_id` from the request body instead of the authenticated token. This is a pattern that should be enforced more systematically; every mutation endpoint should derive `actor_id` from the token, not the body.

## On what remains

1. **Plan 026 WI-3.1 (rotation + revocation lifecycle):** The temporal validity gap flagged by the reviewer needs to be addressed here. `valid_from`/`valid_to` should be checked during principal binding verification.

2. **Plan 026 WI-3.2 (opt-in migration):** Document the path from HMAC-only to per-actor Ed25519. The `verify_principal_binding` flag is the verification side; the signing side needs documentation.

3. **Plan 027 (review assurance):** Depends on Plan 026. The spec entity (WI-4.3) could be the first artifact that carries lineage metadata, but that's not implemented yet.

4. **Test coverage gaps:** The reviewer flagged missing tests for: spec-entity events in principal binding, unknown schemes, hash_alg variations, temporal validity, and `UndefinedTable` backward compat. These should be filed as breadcrumbs.

5. **`_replay.py` complexity:** Consider extracting verification passes (principal binding, timestamps, global chain) into separate verifier functions to reduce the size of `_replay_work_item`.

## Gaps to flag

- **`valid_from`/`valid_to` ignored in principal binding verification** (`_signing.py:475`): Superseded keys can verify events outside their validity window. Should be fixed in Plan 026 WI-3.1.
- **`psycopg.errors.UndefinedTable` catch silently disables binding** (`_replay.py:708-714`): A dropped `principal_keys` table is indistinguishable from a pre-038 schema. Should emit a loud warning.
- **No `key_id` binding check** (`_signing.py:461-516`): Verification succeeds under any non-revoked key for the actor, not specifically the key the event claims to be signed with. Key substitution risk.
- **`_replay_work_item` is ~200 lines** (`_replay.py:588`): Growing complexity; principal binding verification adds another inline block. Extraction would help.
- **InMemory `read_spec_events` had a truncation bug** (fixed, but the pattern of `store.read(limit=N)` then filtering is fragile): Any future code that filters InMemory events should iterate `store.events` directly.
- **Sidecar `SignSpecRequest` no longer has `actor_id`/`actor_kind` fields** (removed as part of H-1 fix): This is a breaking change for any existing sidecar clients, but since this is a new endpoint, there are no existing clients.
