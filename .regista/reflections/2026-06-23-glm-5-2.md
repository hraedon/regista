# Session Reflection — 2026-06-23

**Work summary:** Implemented Plan 022 Phase 1 (entity generalization + crypto-agility envelope v4) for regista. Added `entity_kind`, `entity_id`, `hash_alg` columns to the events table, introduced v4 signing envelope replacing `work_item_id` with `entity_kind`+`entity_id`, added downgrade guard for chained events, and wrote 27 tests. Ran adversarial review via Kimi K2.7, then fixed three critical findings (downgrade guard, archive backfill, witness receipt fields). Filed BC-298 and BC-299 for remaining issues.

## On the project

Regista is a mature, well-structured codebase. The event-sourced model with transactional projection is clean, and the signing/envelope versioning system is thoughtful — the multi-version verification approach (try v4, then v3, then v2, then v1) preserves backward compatibility without re-signing history. The separation between `_events.py` (direct Postgres), `_event_store.py` (shared protocol), and the InMemory backend is good, though it creates surface area for drift (as BC-298 shows).

The plan document (022) is excellent — it clearly scopes what's in/out for each phase and explicitly defers crypto-agility wiring to Phase 2. This made Phase 1 straightforward: land the shape, prove behavior preservation.

## On the work done

**What went well:** The implementation was mechanical but wide — touching 9 source files + 1 migration + 1 test file. The `Event.__post_init__` pattern (setting `entity_id = work_item_id` when None) was a clean way to maintain backward compat without changing every caller. The trigger in the migration handles raw INSERTs that don't specify `entity_id`.

**The downgrade guard was the hardest part.** BC-296 had restricted v3 chained events to v3-only candidates. Extending this to v4 required careful thought: when chain fields are present, only v4 and v3 candidates should be tried (not v2/v1/bare). The first attempt was too strict (only v4), which broke backward compat with v3 events. The fix was to allow both v4 and v3 candidates when chain fields are present.

**What I'd want a second pair of eyes on:** The `verify_event` function's candidate ordering. Currently: stored envelope first (if v4 or v3), then reconstructed v4, then reconstructed v3. The ordering matters for performance but not security (all candidates use the same key). The downgrade guard logic (`has_chain_fields or stored_ver >= 3`) is correct but could be clearer.

## Gaps to flag

- `hash_alg` is in the envelope and schema but does nothing — it's signed data that an auditor could trust incorrectly. This is by design (Phase 2), but worth a comment or validation that it's `"sha-256"` until Phase 2 lands.
- The migration trigger `regista_set_entity_id()` is schema-scoped but uses a plain function name — could collide with other functions if search_path is manipulated. Consider qualifying it.
- `_V4_FIELDS` includes optional fields (`prev_event_hash`, `global_seq`, `prev_global_event_hash`) in the superset check, so an envelope with unknown extra fields could be misclassified. The `issuperset` check is correct but fragile if future envelope versions add required fields.
- The `Event.__post_init__` uses `object.__setattr__` which bypasses frozen protection — standard pattern but worth knowing.
- Tests don't cover the witness receipt field changes end-to-end (only the SQL query was updated). An integration test that creates a witness, fires an event, and checks the receipt body for `entity_kind`/`hash_alg` would be valuable.
