## On the project

Regista is a serious piece of infrastructure engineering — 19K lines, 22
plans, 296 resolved breadcrumbs, 1184 tests. The event-sourcing model with
hybrid projection is sound, and the spec-driven approach (spec.md is
authoritative, breadcrumbs track divergence) is working well. The codebase
has accumulated genuine complexity from real requirements (signing schemes,
witnesses, timestamping, entity generalization), not from speculative
generality.

The biggest structural risk is the one this session validated: the signing
envelope has four versions with complex backward-compat retry, and every
new entity-level feature risks another near-miss where a call site forgets
to forward a field to `sign_event()`. Session 70 fixed `append_event`,
this session fixed `append_transition_event` — the pattern is clear. BC-308
proposes the right resolution: derive version from stored envelope, reject
downgrades, eventually deprecate v1/v2/v3.

The 6 accepted open breadcrumbs are genuinely architectural tensions (sidecar
boundary, migration repair, auth model), not bugs. That's the correct state
for a pre-1.0 library.

## On the work done

The `_events.py` fix was straightforward — explicit parameter forwarding
and query alignment. The kimi reviewer correctly identified that the fix is
safe because `append_transition_event` is work_item-specific, and the
defaults were already correct. But making them explicit is defense against
future entity generalization breaking the transition path silently.

The regression test (`test_transition_event_signature_verifies_with_stored_envelope`)
is the more valuable addition. It verifies that transition events round-trip
through `verify_event()` with v4 envelope + chain fields + entity_kind +
hash_alg. Without this test, removing the explicit parameters from
`sign_event()` would leave all tests green because the defaults happen to
match.

BC-308 was initially imprecise — the kimi reviewer caught that v3 does NOT
introduce entity_kind/entity_id (that's v4's job) and that the "tampered event
acceptance" risk was overstated. The corrected wording focuses on developer
confusion and silent mis-signing, which is the real danger. This was a good
catch.

## On what remains

1. **BC-308 proposed resolution** — derive envelope version from
   `canonical_envelope`, reject downgrades. This is the highest-value
   follow-up. It would eliminate the entire class of "forgot to forward
   a field" bugs by making the signing path version-aware.

2. **Read-path entity-kind filtering** — `read_events_by_work_item` and
   `read_events_composite` in `_events.py` still filter by `work_item_id`
   only. Today this is harmless (all events are work_item entities), but
   it will conflate entities once non-work_item entities exist. The kimi
   reviewer suggested filing a breadcrumb for this.

3. **Process discipline** — Session 69's broken HEAD (35 failures from
   partial work) was a process failure, not a code failure. The CI gate
   exists but only catches problems after push. The `/end` skill's test
   requirement is the right mitigation, but it relies on agent discipline.

## Gaps to flag

- `_events.py:519-553` — `read_events_by_work_item` filters by `work_item_id`
  only, not `(entity_kind, entity_id)`. Latent inconsistency with write path.
  Not filed as breadcrumb yet — kimi reviewer suggested it.

- `_events.py:357` — `Jsonb(stored_payload)` creates a Jsonb but discards
  the result. Dead code from a refactor. Not harmful but noisy.

- `_signing.py:214-233` — `classify_envelope_version()` has two identical
  v4 detection branches (lines 221-224). The first checks `_V4_FIELDS.issuperset(keys)
  and "prev_event_hash" in keys`, the second checks `_V4_FIELDS.issuperset(keys)`
  without the prev_event_hash condition. The first is redundant — if the
  second matches, it would also match. Not a bug, but confusing.

- The `verify_event()` function at `_signing.py:236-412` is 176 lines with
  6+ envelope reconstruction attempts. This is the single most complex
  function in the codebase relative to its criticality. BC-308's proposed
  resolution would simplify this significantly.
