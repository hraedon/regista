## On the project

Regista's codebase is mature and well-organized. The facade decomposition (Plan 007) keeps `__init__.py` manageable, and the contract layer (`_contract.py`) as the single source of truth for validation is a strong pattern. The main tension I observed is the gap between the breadcrumb backlog and the actual code state — many items were fixed across multiple sessions but never transitioned through the review gate, creating a misleading "open work" picture. The two-stage review gate (adversarial_pass → accept) is well-intentioned but practically blocked when all available model lineages have prior work on the same items, making it impossible to satisfy the cross-lineage requirement. This is a process debt issue, not a code issue.

## On the work done

The content_hash validation (BC-301) is a clean, focused change. I'm confident in it because:
- The validation is enforced at three layers: storage (`_links.py`, `_in_memory_links.py`), facade (`_ops.py`, `_in_mem_claim.py`), and API boundary (Pydantic `max_length` in `models.py`).
- The existing `Jsonb.__post_init__` already enforces a 1MB payload size limit via `MAX_JSONB_BYTES`, so the "event payload" half of BC-301 was already covered — I only needed to add `content_hash` length validation.
- The `_check_string_safe` function properly rejects null bytes and unpaired surrogates, which I reuse.
- 9 tests cover both Postgres and InMemory backends, including edge cases (empty string, max-length, null byte, None).

What I'm less sure about: the 256-character limit is reasonable for hash strings but arbitrary. The spec doesn't mention a limit, and the adversarial review flagged this as spec divergence. I didn't amend the spec — that should be done deliberately with a breadcrumb resolution note per the project's conventions.

## On what remains

- **Spec amendment for BC-301**: `spec.md` FR-22b should be amended to document the 256-character `content_hash` limit with a BC-301 resolution note.
- **Review gate items**: 037 and 205 are stuck in `in_review` — the cross-lineage validator blocks all available model lineages because prior sessions used them all. A human reviewer or a new model lineage needs to accept them.
- **037 architectural debt**: The Kimi adversarial review flagged that `validate_work_item_refs` is duplicated between Postgres (`_workflow.py`) and InMemory (`_in_memory_transition.py`) instead of being unified in `_contract.py` (RFC-062). Also, optional `work_item_ref` cannot be cleared to `None` on transition — a pre-existing bug.
- **Sidecar `RequestValidationError` handler**: Pydantic validation failures return raw 422 responses instead of the standard Regista error envelope. This is a broader issue affecting all sidecar models, not just `content_hash`.
- **Open design items**: WI-007 (operator forgery defense), WI-008 (delegation chain), WI-209 (bundle v3), WI-206 (anchoring ops visibility) are all complex design decisions that need human input.

## Gaps to flag

- **Review gate is practically unpassable for items worked by multiple model lineages.** The `adversarial_review` validator rejects any reviewer whose model lineage matches any prior author. With 4+ model lineages all having worked on the regista project, items that have been through multiple sessions cannot be accepted. This needs a process fix (e.g., a human reviewer override, or a time-based staleness threshold).
- **Spec divergence on content_hash limit**: `MAX_CONTENT_HASH_LENGTH = 256` is enforced in code but not documented in `spec.md`. Per AGENTS.md: "do not silently diverge from the spec."
- **`_ops.py` edit risk**: The `validate_mutation_params` pattern appears multiple times in `_ops.py`, making `edit` tool matches ambiguous. I initially hit a wrong-location edit (adding `_validate_content_hash` to `ClaimOps.acquire` instead of `LinkOps.create`). The fix was caught by ruff immediately, but it's a fragile pattern.
- **Breadcrumb reconciliation is partially broken**: The `--apply` flag on `breadcrumb reconcile` crashes on `in_review → closed` transitions because the lifecycle doesn't support that path. The reconcile tool should handle in_review items by transitioning through the review gate or skipping them.
