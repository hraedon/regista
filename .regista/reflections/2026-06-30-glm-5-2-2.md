## On the project

Regista's tamper-evidence spine is genuinely well-designed, and the
spec-vs-implementation gap that Plan 024 exposed (migration 030's comment said
"a hash walk immune to global_seq gaps" while the code sorted by `global_seq`)
is the kind of drift that only shows up under a real integrity sweep. What I
appreciate after this session is that the project *invites* this kind of
scrutiny: the plans are decision-numbered, the spec is the SoT for behavior, and
there's a culture of adversarial review baked into the workflow (commit history
is full of "address adversarial review findings"). That's rare and it's paying
off — the two reviewers caught a genuinely misleading test and a deploy hazard
that I had not flagged in my own review.

The one thing that still feels fragile is the **two append paths**
(`_events.py` vs `_event_store.py`). The genesis fix had to be verified against
both, and the reflection from Session 76 already flagged BC-183 as a lingering
consolidation task. Every future change to chain logic is a "apply it twice and
hope they stay in sync" tax. It's not blocking anything today, but it's the
kind of duplication that breeds the next subtle bug.

## On the work done

The genesis-race fix is the part I'm most confident in and also the part where
the design constraint surprised me. Migration 030 declared `head_hash`/`head_event_id`
NOT NULL — so the obvious "pre-insert a sentinel row" fix required dropping
those constraints. I considered alternatives (advisory locks, nil-UUID sentinels)
and the nullable-columns + NULL-means-genesis approach is the cleanest because
it makes the sentinel *transparent*: `_lock_global_chain_head` already returned
`None` for the genesis case, so returning `None` for a NULL `head_hash` is the
same contract, just now guaranteed to be serialized.

The deploy-ordering hazard is the one thing I want a second pair of eyes on for
*operations*, not code. If migration 035 lands on a schema while old code is
still serving, the first append `TypeError`s loudly. I added a comment, but the
real mitigation is that regista ships migrations atomically with the package
(`run_migrations` in `create_project`) and has migration-checksum drift
detection. Still — in a multi-pod rolling deploy this could bite, and it's
worth a release note.

The adversarial review process itself was the highest-value part. Both
reviewers independently caught that `test_hash_walk_detects_cycle` didn't
actually test cycle detection — it corrupted the genesis event, which removed
the root the walk needs to even reach a cycle. That's exactly the kind of
false-confidence test that a single author doesn't catch. I replaced it with a
direct unit test that constructs a *genuine* reachable cycle (E3 reuses E1's
envelope so `head(E3)==head(E1)`, making E2 a successor of E3), which is the
only way to exercise that branch since a cryptographically-reachable cycle
can't arise from valid signed events.

I'm slightly uncertain about the `test_concurrent_genesis_single_root` test —
it's a probabilistic invariant guard, not a deterministic race reproducer. With
the sentinel it passes reliably; without the sentinel it would likely fail but
could flake-pass under heavy CI load if the workers happen to serialize. I
documented this in the test comment rather than pretending it's deterministic.

## Gaps to flag

- **`_events.py` vs `_event_store.py` duplication** — two independent append
  paths both compute head hashes and advance the chain. The genesis fix covers
  both (both call `_lock_global_chain_head`), but future chain changes must be
  applied twice. BC-183.
- **InMemoryEventStore is not thread-safe** (`_event_store.py:161`) —
  `lock_global_chain_head` is a plain read and `append` does non-atomic
  read-modify-write. The genesis fix is Postgres-only. Documented as
  single-threaded-only; if anyone ever uses `InMemoryRegista` concurrently it
  can still fork. Low risk (test/dev only) but explicit.
- **`test_concurrent_genesis_single_root` is probabilistic** — it's an
  invariant guard, not a deterministic reproducer. Could flake-pass without the
  fix under load. Noted in-test.
- **No negative test for multiple-genesis detection via the DB path** — the
  unit tests cover cycle/fork directly, but `global_chain_multiple_genesis`
  only has indirect coverage. A targeted DB corruption test would close that.
- **Deploy hazard on migration 035** — loud `TypeError` if applied without the
  `_events.py` change. Mitigated by atomic package shipping + checksum drift
  detection, but worth a release note for multi-pod environments.
