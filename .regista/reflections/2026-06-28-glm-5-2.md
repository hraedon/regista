## On the project

Regista is at the point where it's absorbing provenance-critical logic from its consumers. Plan 023 is a convergence play: the same review-gate validators that dossier implemented locally are now regista built-ins, so any consumer (dossier, agent-notes, future faces) gets identical gate enforcement by referencing `adversarial_review` / `human_gate` in their workflow YAML. The `validator_params` mechanism is a clean extension point — it keeps the gate self-describing in the YAML without out-of-band config.

The dual-mode design is the interesting part. Invariant G (cross-lineage adversarial review) is never relaxed — it's the integrity-bearing guarantee. The only thing that toggles is Stage 2: strict requires a human accepter distinct from reviewers; relaxed allows any actor (including the author) to close after an independent cross-lineage pass. This is a policy, not a code path — same function, different parameter. The `_human_gate_builtin` wrapper reads `require_human` from `ctx.validator_params`, which the transition path populates from the workflow YAML.

## On the work done

The port itself was straightforward — dossier's validators were already designed to work with duck-typed contexts (`getattr` throughout), so they slotted into regista's `ValidatorContext` without modification. The `adversarial_review` function is byte-for-byte identical to dossier's (minus docstrings per regista's no-comments convention).

The dual-mode parameterization required touching 8 files across the type system, schema, parsing, and both transition paths (Postgres + InMemory). The `validator_params` field flows: workflow YAML → JSON Schema validation → `build_definition()` → `TransitionDef` → transition execution → `ValidatorContext` → `_human_gate_builtin` wrapper → `human_gate(require_human=...)`.

The adversarial review (GLM) caught one real issue: non-boolean `require_human` values (e.g., `"true"` as a string, `1` as an int) would silently degrade strict mode to relaxed. Fixed by adding an `isinstance(raw, bool)` check that fails closed with a `ReviewRejected`. This is the kind of silent failure that would be catastrophic in a workplace deployment — a quoted `require_human: "true"` in YAML would look correct but silently disable the human gate.

I also fixed `_rebuild_wf` in `_work_items.py` to pass `validator_params` (the adversarial reviewer caught this as L1 — it wasn't on the transition path so had no functional impact today, but was a latent inconsistency).

WI-4 (dossier cross-repo) went cleanly: deleted `dossier/src/dossier/validators.py`, removed the `register_validator` calls from the gateway, added `validator_params: {require_human: true}` to the workflow YAML, and updated test imports. The 34 dossier validator tests + 5 gateway tests pass. One pre-existing test bug in the untracked `test_deferred.py` (`start` from `open` listed as an invalid transition when it's actually valid) — not caused by my changes.

## Gaps to flag

- `src/regista/_review_validators.py:167` — The `_human_gate_builtin` wrapper now validates `require_human` is a boolean, but the JSON Schema (`_workflow_schema.json:114`) declares `validator_params` as a bare `{"type": "object"}` with no property constraints. A schema-level constraint (e.g., `properties: {require_human: {type: boolean}}`) would catch misconfiguration at registration time rather than at transition time. Low priority — the runtime check is the real guard.
- `dossier/tests/test_deferred.py:222` — Pre-existing test bug: `("start", "open")` is listed as an invalid transition, but `start` from `open` is valid in the workflow YAML. The test expects `RegistaError` but the transition succeeds. Not caused by Plan 023.
- The relaxed-mode `human_gate` does not verify that an `adversarial_pass` event exists before allowing `accept`. It relies on the workflow's state machine to ensure `in_human_review` is only reachable via `adversarial_pass`. This is faithful to the original dossier behavior but means a workflow with a path to `in_human_review` that bypasses `in_review` would have a gate that accepts without any review. The plan says "port first, simplify later" — a `pass_ids` emptiness check could be added later if needed.
- `src/regista/_review_validators.py` — The `human_gate` function's relaxed-mode branch skips `_check_separation_of_duties` entirely (per §6.1: self-close permitted). This is correct by design, but it means a non-author non-reviewer agent could accept work in relaxed mode as long as they're not in `pass_ids`. This is the intended relaxation — Stage 1 carries the separation-of-duties weight — but it's worth being explicit about.
