## On the project

The principal-binding verification in `_signing.py` is the security spine of Plan 026. The core function `_verify_principal_binding_core` is shared between the runtime path (`verify_event_with_principal_binding`) and the replay path (`verify_event_dict_principal_binding`), which is good architecture — one place to get security right. But the two call sites construct their `verify_fn` closures differently, and kimi-k2-7's original commit left them asymmetric (one swallowed exceptions, one didn't). That kind of asymmetry is where security bugs hide. The fix this session unifies them.

The `_is_key_valid_at` function is fail-closed when `event_timestamp is None` — meaning if you can't prove WHEN the event was signed, you can't prove it was within the key's validity window. This is the correct security posture for principal keys (which always have `valid_from`), but it's worth noting that any code path that produces a timestamp-less event will fail binding verification. Events in regista always have timestamps, so this is theoretical, but it's a sharp edge.

## On the work done

The adversarial review (dispatched to adversarial-reviewer-glm) was thorough and caught real issues. The most impactful was HIGH-1: `verify_event_with_principal_binding` used a raw lambda `verify_fn=lambda pk: verify_event_with_public_key(event, pk)` while the dict-based replay path wrapped the same call in `try/except Exception: return False`. A malformed event (None signature, missing field) would crash the public API but be handled gracefully by replay. Now both paths swallow exceptions — verification returns False on any crypto error, which is the safe default.

MEDIUM-3 (revoked-key diagnostic) was a quality fix: when an event's key_id matched a revoked principal key, the old code returned `key-id-mismatch` (implying the key never existed). Now it checks for revoked matches first and returns `key-revoked`. This matters for incident triage — key revocation implies compromise, while key-id-mismatch implies substitution.

MEDIUM-4 (pre-filter diagnostic) was the subtlest. When `event_key_id is None` and multiple keys exist, the pre-filter at line 574 removed all invalid keys before the diagnostic loop ran, so the `temporal_skip` and `scheme_mismatch` flags were never set. The function fell through to a generic `signature-verification-failed`. Now the pre-filter result is analyzed directly so operators get the specific cause.

I'm confident in all four fixes. The tests are direct unit tests on `_verify_principal_binding_core` plus integration tests through the public API. The malformed-event test (HIGH-1) would have crashed the old code.

## On what remains

- **HMAC key_id bypass remains intentional** (MEDIUM-1 from the review). HMAC events with a non-matching key_id fall through to try all non-revoked keys rather than returning `key-id-mismatch`. This is correct for backward compatibility (HMAC-only deployments may not have a principal registry), but it degrades diagnostic quality in mixed deployments. Not a security bypass — the signature still has to verify under one of the principal's registered keys. Could be improved by emitting a `key-id-mismatch` warning (not error) for HMAC events.
- **UndefinedTable catch still skips verification** (MEDIUM-2 from the review). The kimi-k2-7 commit added a warning, but the verification is still skipped, not failed. The spec says "Emits warnings, not halts" for principal binding replay, so this is by design. But an attacker who can DROP TABLE principal_keys can bypass all binding verification during replay. This is a DB-access threat, not an application-level one — if the attacker has DDL access, they can do worse.
- **InMemory replay is a complete no-op** for principal binding (MEDIUM-5). One global warning, zero verification. This means no InMemory-based test can catch a binding bug. The Postgres path is the only one that exercises the verification logic.
- **Global chain hash verification** (WI-300) is still open. `prev_global_event_hash` is computed and stored but never verified during replay.
- **Production rotation UX**: `resolve_signing_key` uses `_latest_active_key_for` which is a JSON-order heuristic. After rotation, the new `pk_*` key_id may not be in the keyset, so the signer picks an older key and the event fails the temporal check. This is the correct security answer but confusing DX.

## Gaps to flag

- `src/regista/_signing.py:549-560` — HMAC key_id bypass. Not a vulnerability, but diagnostic signal is lost. Consider a warning-level log for HMAC events with non-matching key_id.
- `src/regista/_keys.py:279-289` — `_latest_active_key_for` uses JSON file order as a proxy for "latest." This is a heuristic that could pick the wrong key after rotation if the key file isn't ordered correctly. The correct fix requires DB-aware key resolution, which is a larger refactor.
- `src/regista/_replay.py:713-723` — UndefinedTable catch caches `[]` per actor and skips verification. An attacker with DDL access can bypass binding. By-design per spec, but worth documenting as a threat-model boundary.
- `src/regista/_in_memory_replay.py:170-176` — InMemory replay emits one global warning and performs zero verification for `verify_principal_binding=True`. No InMemory test can catch a binding regression.
- `tests/test_signer_binding.py` — No test for HMAC key registered in principal_keys with attacker using a different HMAC key (the MEDIUM-1 diagnostic scenario).
