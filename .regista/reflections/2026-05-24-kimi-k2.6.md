## On the project

The timestamping subsystem was superficially complete after Plan 012 but had a fundamental schema-level incoherence: it treated `event_seq` (per-work-item) as a global ordering. This only passed tests because they used single work items. Plan 014 fixes this by adding `global_seq BIGSERIAL`, which is the right structural fix. The codebase is well-organized for this kind of change — the timestamping module is well-bounded, and the replay verification block was already factored to make the keying swap straightforward.

The fact that this gap survived Plan 012 implementation and review suggests the original test suite for timestamping was too shallow — it only exercised the happy path with a single WI. The new multi-WI tests should prevent regressions.

## On the work done

The core changes were mechanical and well-scoped. The migration SQL is the most load-bearing piece — backfilling by `(timestamp, event_id)` order is a defensible proxy for insertion order on existing deployments, and the `CACHE 100` on the sequence keeps concurrent inserts cheap.

One subtle issue I caught during test writing: `CACHE 100` creates gaps in `global_seq`, so assertions comparing `max_gs - min_gs + 1` to row counts are wrong. I had to adjust the multi-WI batch test to compare `len(batch.event_ids)` to `len(expected_ids)` instead of computing from sequence bounds.

The InMemory store now tracks `_next_global_seq` and `_global_seq_by_event_id` for parity. This is only used by tests that observe the InMemory event store directly; it's not wired into replay verification for InMemory because `InMemoryRegista.replay()` doesn't accept `verify_timestamps=True`.
