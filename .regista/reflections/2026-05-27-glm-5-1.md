## On the project

I stand by my earlier evaluation: this is one of the most disciplined codebases I've worked in. The single-source-of-truth contract (`_contract.py`) prevented the heartbeat coalescing fix from being a guessing game — I could see exactly what the shared logic was and only needed to fix the InMemory-specific timestamp comparison. The breadcrumb system made triage straightforward: 11 open, 5 immediately actionable, the rest deferred.

The main structural observation this session: the sidecar is a significant liability. Changing 42 route handlers from `async def` to `def` was a one-line-per-function fix, but the fact that every handler was async in the first place suggests the sidecar was written without thinking about FastAPI's execution model. This is the kind of thing that works fine in development (single-user, no concurrency) and bites in production. The sidecar has 42 endpoints now, zero test coverage on most of them (BC-276), rate limiting that was recently added but is still basic, and auth that's bearer-token-only. It's the weakest part of the system by a wide margin.

The InMemory backend is in good shape. The heartbeat coalescing divergence was a real bug but an easy fix once identified. The replay warning fix was similarly clean. Both had exact parity between Postgres and InMemory once the fix was applied.

## On what remains

1. **BC-276 (test coverage)** is the highest-priority open item. Webhooks, archive, and most sidecar routes have zero tests. This is a real risk given the sidecar is the only HTTP-accessible surface.

2. **BC-277 (events_archive shared sequence)** is a design issue that should be addressed before anyone relies on `events_archive` for anything. The `LIKE events INCLUDING ALL` pattern is a footgun.

3. **BC-271 (CLI dispatch)** gets worse with every new command. The 40-branch if/elif chain is the worst code in the repo.

4. **BC-235 (sidecar hook auth)** needs a design decision before implementation.

5. **BC-213 and BC-270** are accepted/deferred API ergonomics — not urgent.

6. The flaky hook consumer test should be made deterministic. The 30s poll interval makes the test wait up to 15s for the consumer thread to pick up a hook, and the manual `poll_hooks()` fallback competes via `FOR UPDATE SKIP LOCKED`.

## Gaps to flag

- `tests/test_hook_consumer.py:163` — flaky test. The consumer thread and manual `poll_hooks()` compete for hooks via `FOR UPDATE SKIP LOCKED`. Should either make the consumer's poll interval configurable (shorter for tests) or remove the consumer thread from this test and rely solely on manual polling.
- `src/regista/_witness.py:328` — `deliver_pending_receipts` opens a separate connection per witness per delivery batch. Under high event volume with many registered witnesses, this could exhaust the connection pool. Not urgent at homelab scale but worth noting.
- `src/regista/_ops.py:572-575` — the `register_handler` copy-on-write fix creates a new dict on every registration, but `Regista.register_hook_handler` (line 387) still mutates `self._hook_handlers` in-place and reassigns to the consumer. These two code paths are now inconsistent — the HookOps path is copy-on-write, the Regista top-level path is in-place mutation. Both work because they both update the consumer reference, but it's confusing. A future session should unify them.
