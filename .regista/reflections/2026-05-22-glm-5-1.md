## On the project

The codebase is in excellent shape. After 200 resolved breadcrumbs, the dual-backend architecture is clean, `_contract.py` keeps both backends honest, and the property-based tests provide real coverage. The "no comments" convention continues to work well — between spec.md, AGENTS.md, and the breadcrumbs trail, there's enough context to orient without inline noise.

The main remaining structural concern is that `__init__.py` is still ~1200 lines even after facade decomposition. The facades help organize the public surface, but the internal delegation pattern (each old method is a one-liner calling the facade) means the line count didn't actually decrease much. The real benefit is cognitive — consumers now see `sub.work_items.create()` instead of 25+ methods on a flat class. Whether this matters in practice depends on how many non-agent consumers pick up regista.

## On the work done

The parallel sub-agent approach worked well for this session. Plans 007, 008, and 009 are independent — they touch different files and have no ordering dependency. Dispatching three agents simultaneously and then reconciling their outputs was significantly faster than sequential implementation.

The `maintenance_healthy` property required two fix iterations: the sub-agent wrote it to return `False` when no thread is running, but the pre-existing test (BC-185) expected `True`. The correct semantic is "healthy when no problems exist" — no thread running is not a problem, it's a choice. This is the kind of design judgment that sub-agents don't always get right on the first try.

The `_ts_equal` extraction was straightforward and correct. Both replay modules had byte-for-byte identical implementations. The new `_datetime_utils.py` is 38 lines replacing 88 lines of duplication.

## Gaps to flag

- **`tests/test_plan009.py::TestMaintenanceResilience::test_error_does_not_kill_thread`** directly mutates `regista._mgr` to `None` to simulate errors. This reaches into private state and may be fragile if the maintenance thread's error handling changes. Not a real risk today but worth noting.
- **`_ops.py` facade caching uses `hasattr`** — this is idiomatic but slightly unusual. A `_facade_cache: dict` would be more explicit. Not wrong, just a style choice that the next reader should be aware of.
- **The vendored `rfc8785` will drift from upstream** — the cross-validation test is gated behind the `vendor-check` optional dependency. CI should include `pip install -e ".[vendor-check]"` to catch divergence. The test auto-skips if the system `rfc8785` isn't installed, which is fine for development but means the check is easy to miss in CI.
- **`strict_roles` is not tested with the sidecar** — the sidecar passes `strict_roles` through to the constructor, but there are no sidecar integration tests verifying the rejection behavior for unregistered actors over HTTP. Low risk since it's a passthrough, but worth a test if the sidecar gets more consumers.
- **BC-185's `maintenance_cycles_total` counter** — the metric exists in `Metrics.inc` but the `MaintenanceThread` doesn't appear to call it explicitly. The counter may be incremented inside the individual sweep methods instead. Worth verifying the wire-up is complete.
