## On the project

The project is in strong shape. The engineering discipline (breadcrumbs,
worklog, reflections, adversarial reviews) is the real moat — it catches
issues that would otherwise silently rot. The codebase rewards careful
reading; the signing/verification architecture is cleaner than it looks from
the outside, with the scheme registry as the single extension point.

The main risk remains scope growth: 22 plans, 30+ features. The spec is the
guardrail, which is why BC-299 (spec drift) mattered more than its medium
severity suggested. With spec v9 now current, the gap is closed — but it will
drift again if not maintained. The /end skill or a CI check that diffs spec
against API surface would help.

## On the work done

The most consequential discovery was that HEAD was broken (35 test failures)
before I started. Session 68's "1164 passed" was only true with uncommitted
working-tree fixes — the exact BC-302 dirty-tree situation. The user's
parallel commit `324db65` fixed the lower layers but not the upper layers,
and reintroduced the `global_seq` verification bug that Session 68 had
explicitly fixed. This is a cautionary tale about committing partial work and
about the fragility of verification code when envelope fields are conditionally
included.

The adversarial review process was high-value:
- **Kimi (BC-300):** Found the CRITICAL InMemory global_seq bug — events
  never carried global_seq, so the "global" chain walk was actually walking
  dict insertion order. My test passed only by luck. This is exactly the kind
  of silent failure that undermines trust claims.
- **Kimi (BC-297):** Found the InMemory facade parity gap — the facade
  dropped the new params, silently creating HMAC-only witnesses. This would
  have been a confusing production bug.
- **Nemotron (BC-301/asymmetric):** No real bugs, but the "HIGH" finding
  about default is_asymmetric=False was a useful design question (determined
  to be fail-closed, not fail-open).

## Gaps to flag

- `_keys.py:48` — `_asymmetric_schemes()` is called on every
  `resolve_signing_key` (3 call sites). The registry is tiny (2 schemes), so
  perf is negligible, but caching with invalidation on register/unregister
  would be cleaner.
- `_witness.py` — the InMemory delivery path doesn't do HTTP delivery (no
  verification path). This is acceptable since InMemory is for testing, but
  the asymmetry between Postgres (verifies) and InMemory (doesn't deliver)
  is a known limitation.
- Migration 032 adds columns to witness_registrations/receipts but doesn't
  backfill existing rows. Existing witnesses get `key_scheme='hmac-sha256'`
  (the DEFAULT), which is correct (backward compatible).
