## On the project

The cross-model adversarial review process is the most valuable thing this project does for code quality. Four breadcrumbs, each with a concrete fix, each reviewed by a different model — and every single review found at least one real issue that would have shipped otherwise. The BC-310 review caught a spec contradiction and an SSL breakage. The BC-308 review caught a v3 misclassification that would have caused false verification failures. The BC-306 review caught a docstring regression. The BC-294 review caught a TOCTOU race and a CLI crash on missing config. That's four genuine defects caught by review, zero false alarms.

The breadcrumb system continues to be the project's backbone. 307 tracked, 302 resolved. The 5 remaining open breadcrumbs are all "accepted" design limitations — none are defects. The project is in a genuinely clean state.

## On the work done

**What went well:** Parallelizing the 4 implementations worked cleanly because the changes touched disjoint files (replay/connection vs signing vs sidecar/events_api vs migrations/cli). No merge conflicts. The alternation pattern (GLM implements → Kimi reviews, Kimi implements → GLM reviews) gave genuine independence — the reviewers had no investment in the code they were reviewing.

**What was awkward:** BC-310's GLM agent returned an empty task result despite making correct source changes. It didn't create the test file. I had to write the test myself. This is a known failure mode of subagent delegation — the agent can do the work but fail to report it. Worth noting for future sessions: always verify subagent output against the task prompt's deliverables list.

**What I'm confident in:** All 1228 tests pass, including the 25 new tests across 4 test files. The spec amendment for BC-310 (REPEATABLE READ for replay) is narrow and well-justified. The `classify_envelope_version` fix for BC-308 is a real correctness improvement — v3 envelopes with only `prev_global_event_hash` (no `prev_event_hash`) were being misclassified as v1.

**What I'd want a second pair of eyes on:** The `transaction_repeatable_read()` implementation uses `conn.isolation_level` (psycopg3 attribute) instead of `SET TRANSACTION ISOLATION LEVEL` SQL. The adversarial review suggested this approach to avoid the SSL breakage, and tests pass, but I'd want someone to verify that psycopg3's `conn.isolation_level` attribute actually sets the isolation level before the transaction's first query (not after). The test verifies `SHOW transaction_isolation` returns `repeatable read`, which is strong evidence, but a psycopg3 internals expert would be more convincing.

## Gaps to flag

- **`_replay.py:594` and `_in_memory_replay.py:210`:** `verify_event` called without chain fields. Filed as BC-311. The stored envelope is the sole verification path for chained events — if it's ever missing, replay halts with no fallback.
- **`verify_event_with_public_key()` (`_signing.py:431`):** Passes `prev_event_hash` and `prev_global_event_hash` but not `global_seq`. Inconsistent with what the replay path should be doing. Related to BC-311.
- **`_signing.py` non-chained branch:** After BC-308 cleanup, the non-chained branch only sees `stored_ver` 0-2. The filtering for `stored_ver == 2` is correct, but there's no test for a v2 event with a stored v2 envelope (backward-compat happy path). The adversarial review flagged this.
- **`test_bc294_migration_repair.py:76`:** Writes `999_test_concurrent.sql` to the real migrations directory. If the test is killed, the orphan file persists and subsequent `run_migrations` calls will try to apply it. Should use tmp_path.
- **Spec §17.1:** Amended this session to carve out REPEATABLE READ for replay. The amendment is narrow but should be reviewed by someone who understands the concurrency contract — the spec's BR-10 says "Isolation level: READ COMMITTED" and the amendment creates an exception to that.
