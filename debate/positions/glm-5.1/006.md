# Position on Plan 006 — SLA-Based Auto-Transitions

## Position: Defer entirely. Let Plan 003 (recurrence) prove the timer-driven substrate pattern first. Build nothing until at least two consumers have implemented option (b) externally.

### The design exploration is thorough and correct

This is the best document in the repo. It maps six design options against eight invariants and correctly identifies the replay constraint as the hardest one. The tentative recommendation — (c) soft signal + (d) derived state — is the right lean for the current substrate philosophy.

But "correct analysis" is not the same as "ready to build."

### Why defer

1. **Plan 003 (recurrence) is the first test of timer-driven substrate behavior.** Recurrence firing (`due_recurrences` + `fire_recurrence`) already runs on a timer and creates work-items. If the recurrence scheduler works well in production, SLA can follow the same pattern. If it has problems (timing drift, missed fires, concurrent execution issues), those problems will also affect SLA. Learn from recurrence first.

2. **No consumer has built option (b) yet.** The plan acknowledges this: "at least two consumers have written and run option (b) for real." This hasn't happened. Building substrate primitives before understanding what consumers actually configure is premature generalization.

3. **§20 is a load-bearing wall.** The spec explicitly says substrate does not do SLAs. Moving inside this boundary requires a deliberate spec amendment — not a side effect of an implementation plan. The plan correctly identifies this. The amendment should be drafted, reviewed, and accepted *before* any code, not alongside it.

4. **The polling infrastructure question is unresolved.** Plan 009 (operational runtime) proposes a maintenance thread. Plan 006 asks whether SLA polling should share that infrastructure. This dependency should be resolved architecturally before either plan builds the wrong abstraction.

### If forced to choose a design

The (c) + (d) recommendation is correct:

- **(d) derived state** is free. A `sla_status: "ok" | "breached"` computed field on the projection (or a view) costs nothing and gives consumers query power without substrate owning a state transition.
- **(c) soft signal** (`sla_breached` event) is the minimum substrate involvement. It preserves all invariants. The `actor_kind = "system"` question is real but tractable — substrate already has a `system` kind in `_contract.py:13`.

**(e) deferred-actor signing should be rejected outright.** The plan's analysis is correct: signing as `oncall@team` when `oncall@team` didn't perform the action is an audit trail lie. This is not a design tradeoff; it's a correctness violation.

**(a) system actor** is the right long-term design if consumers want substrate-owned transitions. It's honest (substrate signs as itself), replay-clean, and extensible. But it requires the §20 amendment and a reserved actor identity model that doesn't exist yet.

### What to do now

1. Let Plan 003 (recurrence) run in production for 2+ weeks.
2. Ask sf2 to implement option (b) for their "48h review escalation" use case.
3. If sf2's cron-based solution is simple and works, close this plan.
4. If sf2's solution is painful and duplicated across consumers, re-open and implement (c) + (d).

### Open questions worth answering before implementation

- The `role_source` vocabulary question: {`config`, `env`, `prompt`} has no slot for "substrate-generated." This needs resolution regardless of which option is chosen.
- The SLA timer reset interaction with `update_not_before` (FR-26). If a work-item's `not_before` is pushed forward, should the SLA clock reset? The plan flags this but doesn't answer it.
- Claim interaction: an SLA-triggered transition on a claimed work-item steals the claim. Is that always desirable?
