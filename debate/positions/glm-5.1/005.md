# Position on Plan 009 — Operational Runtime (Substrate Daemon)

## Position: Option A (built-in timer thread) only. Subsume the hook consumer. Add maintenance metrics and health indicator. Defer Option B (standalone daemon) indefinitely.

### Option A is sufficient and the right scope

The hook consumer already runs in-process as a background thread. A maintenance thread is the same pattern with more operations. No new deployment artifact, no new network boundary, no shared key material problem. Consumers who want maintenance call `start_maintenance()`. Consumers who don't, don't.

Option B (standalone daemon) adds a deployment artifact, shared HMAC key material between processes, health-check endpoints, and signal handling — all for a use case that doesn't exist yet. The sidecar (Plan 005) already covers the "separate process" deployment model. A third process is speculative.

**Defer Option B indefinitely.** If a deployment scenario emerges where neither in-process embedding nor the sidecar is appropriate, re-evaluate then.

### Subsume the hook consumer

Agree with kimi-k2p6-turbo: `start_maintenance()` should subsume `start_hook_consumer()` / `stop_hook_consumer()`. Having two separate threading APIs is confusing. The maintenance thread runs the hook dispatch loop alongside sweeps and recurrence firing.

Deprecation path: `start_hook_consumer()` becomes an alias that calls `start_maintenance(hook_poll_interval=...)` if no maintenance thread is running, or logs a warning if one is. Remove the alias after one version.

### Maintenance metrics are essential

kimi-k2p6-turbo's list of operational counters is correct and worth reproducing:

- `substrate_maintenance_sweeps_total` — cycles executed
- `substrate_maintenance_claims_swept_total` — claims actually swept
- `substrate_maintenance_partitions_created_total` — event partitions created
- `substrate_maintenance_recurrences_fired_total` — recurring work-items created
- `substrate_maintenance_hook_leases_swept_total` — stranded leases recovered
- `substrate_maintenance_errors_total` — already in the plan

Without these, an operator cannot distinguish "maintenance thread is running and healthy" from "maintenance thread is running but finding nothing to do" from "maintenance thread is silently failing."

### Health indicator

```python
@property
def maintenance_healthy(self) -> bool:
    """True if the maintenance thread is alive and its last cycle succeeded."""
```

This is the right shape. Consumers can expose it as a health check without wiring callbacks.

### Backoff-when-idle is a good idea with a caveat

Exponential backoff when a cycle finds no work reduces DB load for low-traffic projects. The caveat: claim expiry timing matters. If a claim expires during a backoff period, the work-item stays unclaimable for longer than the TTL. This is probably acceptable (the next acquire_claim can steal it), but worth documenting as a timing tradeoff.

Recommendation: apply backoff to partition checks and recurrence polling only. Claim sweeps and hook lease sweeps should run at fixed intervals because their timeliness matters for correctness.

### Spec amendment wording

kimi-k2p6-turbo's proposed wording is better than the plan's:

> "Substrate provides optional background maintenance threads for timer-driven infrastructure operations. It does not require a separate daemon process for correctness."

This preserves the "library, not daemon" framing while acknowledging the thread. Use this.

### Sequencing

After Plan 007 (facade decomposition). The maintenance methods (`start_maintenance`, `stop_maintenance`, `maintenance_healthy`) are infrastructure-level and belong on the top-level `Substrate` class. Plan 007 clarifies that boundary by moving domain methods to facades.

If Plan 007 is deferred, Plan 009 can still proceed — the maintenance methods are already infrastructure-level regardless of whether domain methods are on facades.

### Risk

The primary risk is the maintenance thread dying silently. The plan's `on_error` callback + `substrate_maintenance_errors_total` counter is the right mitigation. The `maintenance_healthy` property gives consumers a polling signal. If the thread dies, the counter stops incrementing and `maintenance_healthy` returns `False`. This is sufficient for any reasonable monitoring setup.
